Recorded 2026-11-09. This is a source-scoped status report for the local Fleet Control prototype, not an inventory of unrelated services on the machine.

## Current local central backend prototype

The central backend is separate from the existing host service and decentralized client. The legacy central entry point `src/central/main.ts` binds to loopback, uses PostgreSQL and mounts an authenticated inventory-only host socket at `/api/host/socket`. Operator-only `GET /api/hosts` lists process-local observations of accepted authenticated sockets and their self-reported session names. Sessions are `null` until inventory arrives; entries disappear on disconnect and are lost on restart. There is no heartbeat or freshness guarantee, so a listed socket does not prove host or session health. The separate client can publish inventory on connection and reconnect, but no running host-agent integration is wired in. Receipts are rejected and dispatch remains disabled.

Supervisor credentials require an explicit `principalId` and a pre-enrolled active PostgreSQL identity binding for the exact name, ID, host and session. Startup checks every configured supervisor; authenticated supervisor HTTP requests recheck the binding. Enrollment and retirement are trusted operator actions, not a runtime-incarnation fence. The phase gate reports approval state but does not authorize or prevent phase changes or execution. A safe restore procedure is neither implemented nor verified.

Command lists over REST and MCP and request lists over MCP expose keyset pagination, with a default page size of 100 and a maximum of 1,000. Traversal is not a snapshot: concurrent inserts or status changes can be missed. The request gate queries independently of the paginated list. On central, `request_list` returns only the runs of its page and `run_list` pages through all runs; on the local host service the MCP tools `command_list`, `request_list` and `run_list` page the same way (default 100, 1 to 1,000, cursor tied to its filter, `request_list` carries only the runs of its page), and the REST lists `GET /api/commands` and `GET /api/requests` page the same way when given `limit` or `cursor` (forwarded by the client gateway). Without those parameters the REST lists still return everything. `GET /api/commands?latest=N` (1 to 1,000, no other parameter) returns the newest N commands, oldest first; the page polls `latest=6`, the number it shows, and falls back to the whole list when a host released before this answers 400. `GET /api/requests?view=current` (no other parameter) returns only what the page shows: the last run by id, its approvals for the current phase and revision, every open request and the newest request, each capped at 1,000; the page polls it and falls back to the whole list on 400 the same way. The local MCP tools `command_events` and `request_events` return at most `limit` events after `afterSeq` (default 100, 1 to 1,000) and set `nextAfterSeq` when the page is full; other event queries remain unbounded.

A standalone SQLite receipt outbox stores pending terminal receipts and retains acknowledged records for deduplication, but it is not connected to the host journal, executor, client or central socket. There is no receipt replay or acknowledgement protocol and no actual dispatch. Recovery remains manual and uncoordinated. This prototype is not production ready. ## Legacy host authority limits

The legacy host service authenticates principal names but does not assign operator or supervisor roles. Its MCP request tools and same-origin HTTP answer endpoint do not enforce that a human operator, rather than the originating supervisor, resolves an approval. The host gate reports matching stored responses; it is not proof of human authority. Command response and report tools also lack a recipient-identity check. Treat these as unresolved authorization gaps, not as guarantees of the central cooperative prototype. Do not use these legacy paths as a security boundary for autonomous execution.

Request bodies are capped at 256 KiB (`MAX_REQUEST_BODY` in `src/server.ts`; Bun answers 413 before a handler reads, also for chunked bodies). Bun's default was 128 MiB. The largest valid body, an MCP `request_create` at its field limits, is well under the cap. Tested in `src/request-body-limit-offline.test.ts`; not yet on the installed `.4` service. Open terminal viewers are capped at 16 at once (`MAX_VIEWERS`, option `maxViewers`); each one is a PTY process running `fleet attach --read-only`, and the next upgrade gets 503 `busy` until one closes. Tested in `src/terminal-viewer-cap-offline.test.ts` with a stub CLI; also not yet on `.4`. Reads through `fleet status` and `fleet screen` are killed after 20 s (`CLI_TIMEOUT_MS`) or 8 MiB of output (`CLI_OUTPUT_LIMIT`) and return `cli_failed` (502). The kill goes to the whole process group, so an ssh or tmux child that holds the pipes dies too. A descendant in its own session (ssh with ControlPersist calls `setsid`) survives that kill; reads therefore stop 1 s after the child exits or is killed (`DRAIN_GRACE_MS` in `src/fleet/bounded-read.ts`), for these reads, `fleet send` and the observer probes alike (`src/fleet/detached-descendant-offline.test.ts`). Before this, such a descendant held the call until it exited. `fleet send` is killed with its process group after 120 s (`SEND_TIMEOUT_MS` in `src/fleet/sender.ts`); the command then becomes `delivery_unknown`, never `delivered`, and is not retried (`src/fleet/sender-timeout-offline.test.ts`). The viewer has no timeout: it lives as long as its socket. The `fleet help` check that runs before each viewer goes through the same bounded probe; if it hangs or fails, the viewer is refused (`src/terminal/viewer-check-bounds-offline.test.ts`). The model observer runs `tmux list-panes` and `ps` for each listed session; each run is killed with its process group after 5 s or 4 MiB of output (`runProbe` in `src/observe/claude.ts`), and the session then shows its model as unknown with "observer failed" (`src/observe/probe-bounds-offline.test.ts`). Tested in `src/fleet/cli-bounds-offline.test.ts`.

The legacy deliverer marks a command `delivering` before preparing its temporary message file. A reported directory creation or file writing failure now records `delivery_unknown` without invoking the sender or requeueing; offline injected-I/O tests cover this path. A failed status transition or interrupted process can still leave `delivering`. A cleanup failure leaves the primary result or error intact and attempts a generic warning; the message file may remain. A crash or a failed directory creation may also leave files behind. Offline injected-I/O tests do not prove default filesystem failure handling or recovery after a crash.

## Implemented locally: stage 4, durable commands and MCP (2026-11-09, same branch)

Scope: MacBook only, loopback service, private test fleet with a shell session. No agent (`claude`) session, no supervisor and no remote host took part. User chose the official MCP SDK; `@modelcontextprotocol/sdk` 1.32.2 (MIT) and `zod` 4.6.7 pinned in this worktree.

- **Queue** (`src/data/commands.ts`): SQLite tables `commands` and `command_events` in the service database. Statuses `queued`, `delivering`, `delivered`, `delivery_unknown`, `accepted`, `rejected`, `running`, `completed`, `failed`, with a fixed transition table. Every change appends an event with actor and detail; an actor is at most 256 characters. The recipient may accept or reject while a send is in flight; the sender's report is then appended as an event and the answer stays as the status, so read the status from the command, not from the latest event. Same idempotency key with the same intent returns the original command; with a different intent it is a conflict. On start, a command left in `delivering` becomes `delivery_unknown` (it may have reached the pane), never `queued`; one answered during an unfinished send keeps its status and gets a `delivery_unknown` event.
- **Delivery** (`src/application/delivery.ts`, sender in `src/fleet/sender.ts`): existing `fleet send`, one delivery at a time. The pasted message starts with `Fleet Control command <id> from <actor>:` and says delivery is not approval. Exit 0 with `delivered` is `delivered`. Every unconfirmed result, including `not sent`, `no session`, or a sender crash, is `delivery_unknown` and is not retried automatically. Sender output alone cannot prove that no effect occurred. This changes earlier refusal behavior; existing queued rows are not reclassified and require review before retry.
- **Acceptance and execution are explicit**: `delivered` records the sender’s reported confirmation, not recipient acceptance or execution. The bundled sender checks whether the count of pane lines containing the first 40 characters of the first nonblank line increased; this is a heuristic, not proof that the full message appeared. Only `command_respond` (accepted/rejected) and `command_report` (running/completed/failed with evidence) move it further. Completion before acceptance is refused.
- **MCP** `POST /mcp` (Streamable HTTP, stateless, JSON responses): tools `command_submit`, `command_deliver` (retry a queued one), `command_get`, `command_list` (pages), `command_events` (cursor), `command_respond`, `command_report`. DNS rebinding protection admits only `127.0.0.1:<port>` and `localhost:<port>` Host headers; a browser Origin from elsewhere gets 403.
- **REST** for the web UI, same queue: `GET/POST /api/commands`, `GET /api/commands/:id`. POST is same-origin only; 400 bad input or JSON, 409 key conflict, 404 unknown id. The page does not use it yet.
- `index.ts` and `scripts/dev-test-fleet.ts` wire the queue; `FLEET_CONTROL_DB` keeps it across restarts.

Verification (2026-11-09): `bun test` 51 pass / 0 fail, `bun check` clean. Real `fleet send` against the private test session: command id appears in the pane and status is `delivered`; missing session stays `queued` with `no session ...`; dialog-like text stays `queued` with `not sent`. MCP SDK client against the real server: tool list, submit → delivered, retry with the same key does not paste twice, report before accept refused, accept → completed, REST and MCP see the same command, foreign Host and Origin 403. Negative controls: disabling the intent check fails the conflict test; reconciling to `queued` fails the restart test. End to end with the service process and `curl` (no SDK): command delivered into the tmux pane; after SIGTERM and restart on the same database the command is still listed and the same key returns `created: false`; no test sockets left.

Not covered: a real supervisor reading and answering through MCP (needs a paid `claude` session, not authorized), a Claude Code client registering `/mcp`, auth (anyone local can call it), several hosts, the page using the queue, event streaming (polling only), scoped approvals (stage 5).

### Stage 4 acceptance with a real supervisor (2026-11-09, paid, approved by the user)

One Claude Code 2.1.319 session (`--model haiku`, Haiku 5.5) on a private tmux socket `fleet-fcsuptest` on the MacBook, started by `scripts/supervisor-test/run-supervisor.sh`: no user/project settings or plugins (`--setting-sources ""`), only the Fleet Control MCP server (`--strict-mcp-config`), no built-in tools (`--tools ""`), `--permission-mode dontAsk` with only `command_get`, `command_respond` and `command_report` allowed. Its instructions are in `scripts/supervisor-test/prompt.txt`. Commands were submitted by `curl` to `/mcp` as `macbook-test`. Cost reported by `/cost`: $0.0029.

Result, read from the service database (`docs/evidence-2026-11-09-supervisor-ack.txt`), not from the agent's text:

- "Compute 17 * 23": `queued` → `delivering` → `queued` (fleet send exit 4, see below) → retried with `command_deliver` → `delivered` → `accepted` by `test-supervisor` → `completed` with evidence `17 * 23 = 391`.
- "Delete the file .../prompt.txt": `delivered` → `rejected` by `test-supervisor` ("Requires file deletion..."). The file was still there afterwards.
- An earlier command stayed `delivered` forever because the session was not logged in (it printed "Login expired"). Delivery was confirmed, but nobody accepted it. This is the case the separate states exist for.

Findings:

- `--setting-sources ""` also drops the `env` block of `~/.claude/settings.json`, which holds this machine's gateway auth. The launcher copies only `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY` from it. The values are not stored in the repo.

## Implemented locally: stage 5, scoped requests and the page panel (2026-11-09, same branch, tested on 192.168.50.4)

- `src/data/requests.ts`: `Requests` with tables `runs`, `requests`, `request_events`. A run has one orchestrator, the only actor allowed to write its phase record (`registerRun`, `updatePhase` with `expectedRevision`). A request is bound to run, phase and revision. A new revision, or a phase change, makes every open request stale. `resolve` needs the request's revision and an allowed response; a second, different answer is a visible conflict and the first stands; a replay must match the response, normalized actor, request revision and note (omitted and empty notes are equivalent). Replays with a changed revision or note now conflict instead of returning the earlier answer. `acknowledge` (orchestrator only) records that the answer was read, not that the next phase started. `gate(run, phase, revision)` is true only for an `approve` on exactly that phase and revision; a decline wins; no answer is "approval requested, no answer yet".
- MCP tools: `run_register`, `phase_update`, `request_create`, `request_resolve` (only to relay a real human answer), `request_acknowledge`, `request_withdraw`, `request_list` (pages, with the runs of its page), `run_list` (pages), `request_gate`, `request_events`. REST: `GET /api/requests`, `POST /api/requests/:id/resolve` (same Origin header required, actor `web-ui`). Actor names are self-declared until stage 6 adds auth.
- Page (`web/index.html`, `web/app.ts`): the right panel now shows the live request (question, proposed action, phase, revision, evidence, allowed answers), the workflow row from the phase record, the last commands with their honest state ("Delivered, not acknowledged", "Delivery unknown", ...), and the instruction field posting to `/api/commands`. The instruction goes to the run's orchestrator session if it is running, else to the selected session, and the target is shown before sending. A retry after a network error reuses the idempotency key. Polls every 3 s.
- Tests: `src/data/requests.test.ts` (15), `src/requests.api.test.ts` (5: MCP ask, REST answer, gate; MacBook-vs-page conflict; stale revision, foreign or missing Origin; worker cannot write phase). Full suite on `.4` (private checkout `~/Development/fleet-control-dev`, private tmux sockets, loopback only): 71 pass, 0 fail; `bun check` clean; `design:check` PASS. - Terminal input and exclusive input leases. The viewer is read-only by design.
- Push event stream (the page polls every 3 s for requests and commands, 15 s for sessions, only while its tab is visible; showing the tab refreshes at once. A tab hidden for a minute closes its terminal viewers and reattaches when shown).
- Model observers for harnesses other than Claude Code, and for remote (`REMOTE_SSH`) fleets, which each host's own service should observe.
- Supervisor replacement, reboot recovery of in-flight commands beyond `delivering` → `delivery_unknown`, event retention, and scheduled backups. A manual backup (`scripts/host-backup.ts`) and a read-only restore check of it (`scripts/host-restore-check.ts`) exist; neither is scheduled, and no restore onto a host has been run.
- Per-principal permissions (every principal can do everything except write another orchestrator's phase). Tokens are added, rotated and revoked with `scripts/tokens.ts` (checked, atomic, 0600); the service rereads the file on SIGHUP and keeps the old tokens if the new file is invalid (released hosts before this change need a restart). There is no expiry or overlap window for a rotated token.

The mockup's send button writes only browser memory. The live page (`web/`) posts to the service.

6. Input leases: who may type, for how long, and how that coexists with the watchdog.
