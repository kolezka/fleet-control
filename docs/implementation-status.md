## Workstation onboarding, configuration and project-owned decisions (2026-11-25, PR #222, on `main` as `19afaaf`, not released, not deployed)

From Terminal Studio v21 (`.design/briefs/operator-workspace-nov24`). Nothing here ran against a real host, a real gateway or a real fleet.

- **Plan before enrollment.** On `/add-host`, Fresh install now shows a preview first (workstation, checkout, new service, certificate, operator identity, SSH) and sends nothing. Editing a field or switching mode drops the preview. "Start enrollment: make token and command" is a separate button and uses the existing begin step. Connect for a running host is unchanged.
- **Saved plans.** "Save plan only" stores the plan in `<gateway config>.workstation-plans.sqlite` through `GET/POST /api/enroll/plans`, behind the same `FLEET_CONTROL_ENROLL=1` switch and Origin check as enrollment. A saved plan makes no token, adds no host and runs nothing. The store only inserts and refuses a second plan with the same id. A plan whose id belongs to a host already in the config is refused (400). Plans survive a gateway restart; hosts being added still do not. Reading the list never creates or changes the store file: no file means no plans. An unreadable store, or a file that is not a plan store, answers 500, the cause goes to the gateway log, and the page says "Cannot read saved plans." instead of showing an empty list.
- **Workstation configuration.** `/workstation?host=<id>` (linked from the host view, only with the manage switch) edits display name, group, description and the harness preferred for new sessions (`claude-code`, `deepseek-harness` or not set). It shows the changes before saving. `GET/POST /api/manage/<id>/profile` saves only when the caller's snapshot still matches the stored one (409 otherwise), under the config lock, by temp file and rename. Address and credential files cannot be changed here. Configs without `profile` stay valid.
- **Harness preference.** The agent form for a host starts on DSH when the host's preference is `deepseek-harness`. The operator can still pick another kind. It changes no running session and is not the observed harness.
- **Project ownership.** `run_register` (MCP and store) takes `projectId` and `taskId` together. They are kept in a separate table (`run_project_ownership`) and never change for a run; registering the same run again with a different owner is a conflict. Runs registered without them have no owner, and nothing is guessed from the host or session name. Current requests carry the owner of their own run, so two projects on one host stay apart.
- **Decisions in the centre.** The machine's request panel no longer has answer buttons. A request with an owner shows "Open <project> / <task>"; one without says "Project and task not assigned." and shows "Open unassigned decisions". A request with only a project or only a task, or with an owner value that is not a name, says "Project and task could not be read. This request cannot be answered.": it is in no review, because the host service stores both or neither and the page does not guess. The review in the centre lists only that project and task, or only the requests with no owner. An answer is sent only from the open review, for a request that belongs in it, on a host whose request state was read, for an open request at the shown revision with a response it allows. The unassigned review exists because managed orchestrators (`src/fleet/agents.ts`) and `scripts/run-file-sync.ts` register runs without a project and wait for an answer; without it their requests could not be answered from the page. The request revision is escaped in both panels. Picking another host, or the host becoming cooperative, closes the review. Answer, acknowledgement and execution stay separate states.
- **Limits.** The review reads the selected host's current requests, not a project's requests across hosts or its history. There is no project list, task list or Workspaces navigation in the product yet. Managed orchestrators and `scripts/run-file-sync.ts` still register runs without a project and task, so their requests land in the unassigned review of their host; nothing assigns an owner afterwards. The page does not check the fields of a request it reads from a host (`parseCoord` in `web/host-state.ts`); it escapes them when it shows them. A field of the wrong type, such as a number where the question text belongs, makes the request panel fail to draw for that host (seen with a probe; the same code was there before PR #222). The plan id check covers hosts in the config only: a plan can take the id of a host whose enrollment has started but not finished, and enrollment does not look at saved plans, so a plan stays listed after a host with its id is added. A profile save checks the name and profile fields but does not parse the whole resulting config before writing it. Failed plan and profile writes are logged with their cause; nothing else about them is recorded. A saved plan cannot be edited, removed or turned into an enrollment from the list. The profile's group and description are stored and edited but the sidebar does not group by them yet. Host status (disk, RAM, last contact) from v21 is not built.

## Host part: certificates, Tailscale Serve and other services (2026-11-23, branch `feat/infra-status`, not released)

With `FLEET_CONTROL_ADMIN=1` the page's Fleet section gets a Host part for operators.

- Certificates: the service's LAN certificate (`FLEET_CONTROL_TLS_CERT`) and tailnet certificate (`FLEET_CONTROL_TAILNET_TLS_CERT`) with names, end date and days left. The tailnet one can be renewed from the page (typed `renew`): the service asks `tailscale cert` for new files beside the old ones, checks that the certificate names `FLEET_CONTROL_TAILNET_NAME` and that the key matches, keeps the old permission bits, then renames them over. Any failure leaves the old files. The service also checks once at start and then daily, and renews when fewer than 30 days are left. Bun cannot swap a running listener's certificate, so a renewed certificate is used from the next service start (the page says so). The LAN certificate is made by hand (mkcert) and only shown.

- Other services: only those named in `FLEET_CONTROL_OTHER_SERVICES` (`name=launchd:<label>`, `name=systemd:<unit>.service` or `name=compose:<dir>:<service>`, comma separated) are shown with their state, and an operator restarts one by typing its name (`launchctl kickstart -k`, `systemctl --user restart`, `docker compose restart <service>`). ## Tokens from the page (2026-11-23, released in 238817a)

With `FLEET_CONTROL_ADMIN=1` the fleet section also lists the host's tokens file: names and roles only, never hashes. An operator can rotate a line (the new token is shown once on the page, kept nowhere, and only its hash goes into the file) or revoke it, each after typing the name. The file is changed under the same lock as `scripts/tokens.ts`, written atomically with mode 0600, and the running service takes the new file at once (no SIGHUP); sockets of a revoked token close. Any operator may rotate another operator's line and receives its new token: operators are equals here, so this is not an escalation, but it hands over that identity. Refused: the caller's own line (the gateway changes its own link, below), managed `fc-` agent lines (they end with the agent), unknown names, and revoking the last operator. Each check runs again on the file as it is under the lock.

The gateway (with `FLEET_CONTROL_ENROLL=1`, the same switch as adding hosts) can also rotate its own token for a host and remove a host, at `/api/manage/<id>/rotate|remove` after typing the host id. Rotate makes the new token on the gateway, writes it beside the old file, sends the host only the SHA-256 (`POST /api/token/replace`), and puts it in place only after the host took it; a refusal or a missed answer leaves the old token working (with no answer it asks the host which token it knows). Only a `token-<id>` file the gateway made next to its config is rotated or deleted; a hand-named token file is left alone. Remove with revoke first deletes the gateway's line on the host (`POST /api/token/revoke`, refused for the last operator); a host that cannot answer is removed only without revoke, and the page says the line stays on the host.

## Current local central backend prototype

The central backend is separate from the existing host service and decentralized client. The legacy central entry point `src/central/main.ts` binds to loopback, uses PostgreSQL and mounts an authenticated inventory-only host socket at `/api/host/socket`. Operator-only `GET /api/hosts` lists process-local observations of accepted authenticated sockets and their self-reported session names. Sessions are `null` until inventory arrives; entries disappear on disconnect and are lost on restart. There is no heartbeat or freshness guarantee, so a listed socket does not prove host or session health. The separate client can publish inventory on connection and reconnect, but no running host-agent integration is wired in. Receipts are rejected and dispatch remains disabled.

Supervisor credentials require an explicit `principalId` and a pre-enrolled active PostgreSQL identity binding for the exact name, ID, host and session. Startup checks every configured supervisor; authenticated supervisor HTTP requests recheck the binding. Enrollment and retirement are trusted operator actions, not a runtime-incarnation fence. The phase gate reports approval state but does not authorize or prevent phase changes or execution. A safe restore procedure is neither implemented nor verified.

Command lists over REST and MCP and request lists over MCP expose keyset pagination, with a default page size of 100 and a maximum of 1,000. Traversal is not a snapshot: concurrent inserts or status changes can be missed. The request gate queries independently of the paginated list. On central, `request_list` returns only the runs of its page and `run_list` pages through all runs; on the local host service the MCP tools `command_list`, `request_list` and `run_list` page the same way (default 100, 1 to 1,000, cursor tied to its filter, `request_list` carries only the runs of its page), and the REST lists `GET /api/commands` and `GET /api/requests` page the same way when given `limit` or `cursor` (forwarded by the client gateway). Without those parameters the REST lists still return everything. `GET /api/commands?latest=N` (1 to 1,000, no other parameter) returns the newest N commands, oldest first; the page polls `latest=6`, the number it shows, and falls back to the whole list when a host released before this answers 400. `GET /api/requests?view=current` (no other parameter) returns only what the page shows: the run registered or given a phase update last (`updated_at`, ties by id; requests do not move it), its approvals for the current phase and revision, every open request and the newest request, each capped at 1,000; the page polls it and falls back to the whole list on 400 the same way. Hosts released before PR #203 pick the last run by id instead, so an old run can hide a new one, and the page shows their choice. The local MCP tools `command_events` and `request_events` return at most `limit` events after `afterSeq` (default 100, 1 to 1,000) and set `nextAfterSeq` when the page is full; other event queries remain unbounded.

A standalone SQLite receipt outbox stores pending terminal receipts and retains acknowledged records for deduplication, but it is not connected to the host journal, executor, client or central socket. There is no receipt replay or acknowledgement protocol and no actual dispatch. Recovery remains manual and uncoordinated. This prototype is not production ready. ## Legacy host authority limits

The host service gives every token one role, set in a third column of the tokens file: `operator`, `agent` or `viewer`. A line without a role is an `agent`, so an old file still starts the service and gains no authority, but a page or gateway token written before roles can no longer answer requests until it is given `operator` (`scripts/tokens.ts role <principal> operator <file>`, then SIGHUP). Only an `operator` may answer a request (`POST /api/requests/:id/resolve` and MCP `request_resolve`); an `agent` gets 403 `forbidden` (MCP: a `forbidden:` error), even for a request it asked itself. An `agent` may still queue, deliver, answer and report commands and write its own runs, phases and requests. A `viewer` reads sessions, terminals, commands and requests and is refused every change on REST and MCP. `/api/whoami` returns the role. A role change on SIGHUP closes terminal sockets opened under the old role. The role says which token may record an answer, not that a human typed it: whoever holds an operator token (the gateway, the browser, the DSH panel) can answer. Without auth (loopback only) there are no roles. Tested in `src/roles.test.ts` and `scripts/tokens.test.ts`. The host gate reports matching stored responses; it is not proof of human authority. Command response and report tools still lack a recipient-identity check. Treat these as unresolved authorization gaps, not as guarantees of the central cooperative prototype. Do not use these legacy paths as a security boundary for autonomous execution.

With auth on, the host service refuses a command whose text contains one of its current tokens, on REST (400 `invalid`) and on MCP `command_submit` alike. Nothing is stored or delivered, because delivered text stays in the pane's scrollback where every terminal viewer can read it. MCP `command_deliver` checks the stored text of a queued row again, so a row queued before this guard, or by an instance without auth, is not delivered through this service while it holds a current token; rows in other statuses come back unchanged as before. A second instance without auth on the same database still stores and delivers such text unchecked, because it holds no token hashes. The check looks at whitespace-separated words, runs of token characters and runs of base64url characters inside them, so quotes, `Bearer `, `token=` or `?t=` do not hide a token. It also checks every 43-character window, the length of tokens made by `newToken` (`scripts/tokens.ts`, `scripts/new-token.ts`), so such a token glued to other characters (`pre_<token>x`) is caught too; a hand-made token of another length is caught only at word or run boundaries. A full 4,000-character scan takes about 1 ms. Text whose trimmed length is over the 4,000-character cap gets the usual length error without a scan; a token padded with whitespace past the cap is still refused. It does not catch a token that was split, encoded or changed, nor tokens of other hosts or services. Tested in `src/auth.test.ts`. A check of the `.4` test session `probe-shell` on 2026-11-19 found no current token in its scrollback (each candidate word hashed and compared with the tokens file, with a positive control). The tokens file was last changed on 2026-11-16, before the leak was reported, so no rotation hides a match. The scrollback held only command IDs and test markers such as `FC-PAGE-<8 hex>`, a marker sent from the page; the reported "page token" was most likely that marker, which is not a credential. That reading is an inference, not confirmed by the person who reported it. The pane was cleared with `tmux send-keys -R` and `clear-history` (no input sent; `cat` kept its pid) and afterwards held no lines.

Request bodies are capped at 256 KiB (`MAX_REQUEST_BODY` in `src/server.ts`; Bun answers 413 before a handler reads, also for chunked bodies). Bun's default was 128 MiB. The largest valid body, an MCP `request_create` at its field limits, is well under the cap. Tested in `src/request-body-limit-offline.test.ts`; not yet on the installed `.4` service. Open terminal viewers are capped at 16 at once (`MAX_VIEWERS`, option `maxViewers`); each one is a PTY process running `fleet attach --read-only`, and the next upgrade gets 503 `busy` until one closes. Tested in `src/terminal-viewer-cap-offline.test.ts` with a stub CLI; also not yet on `.4`. Reads through `fleet status` and `fleet screen` are killed after 20 s (`CLI_TIMEOUT_MS`) or 8 MiB of output (`CLI_OUTPUT_LIMIT`) and return `cli_failed` (502). The kill goes to the whole process group, so an ssh or tmux child that holds the pipes dies too. A descendant in its own session (ssh with ControlPersist calls `setsid`) survives that kill; reads therefore stop 1 s after the child exits or is killed (`DRAIN_GRACE_MS` in `src/fleet/bounded-read.ts`), for these reads, `fleet send` and the observer probes alike (`src/fleet/detached-descendant-offline.test.ts`). Before this, such a descendant held the call until it exited. `fleet send` is killed with its process group after 120 s (`SEND_TIMEOUT_MS` in `src/fleet/sender.ts`); the command then becomes `delivery_unknown`, never `delivered`, and is not retried (`src/fleet/sender-timeout-offline.test.ts`). The viewer has no timeout: it lives as long as its socket. The `fleet help` check that runs before each viewer goes through the same bounded probe; if it hangs or fails, the viewer is refused (`src/terminal/viewer-check-bounds-offline.test.ts`). The model observer runs `tmux list-panes` and `ps` for each listed session; each run is killed with its process group after 5 s or 4 MiB of output (`runProbe` in `src/observe/claude.ts`), and the session then shows its model as unknown with "observer failed" (`src/observe/probe-bounds-offline.test.ts`). Tested in `src/fleet/cli-bounds-offline.test.ts`.

The legacy deliverer marks a command `delivering` before preparing its temporary message file. A reported directory creation or file writing failure now records `delivery_unknown` without invoking the sender or requeueing; offline injected-I/O tests cover this path. A failed status transition or interrupted process can still leave `delivering`. A cleanup failure leaves the primary result or error intact and attempts a generic warning; the message file may remain. A crash or a failed directory creation may also leave files behind. Offline injected-I/O tests do not prove default filesystem failure handling or recovery after a crash.

## Implemented locally: stage 4, durable commands and MCP (2026-11-09, same branch)

Scope: MacBook only, loopback service, private test fleet with a shell session. No agent (`claude`) session, no supervisor and no remote host took part. User chose the official MCP SDK; `@modelcontextprotocol/sdk` 1.32.2 (MIT) and `zod` 4.6.7 pinned in this worktree.

- **Queue** (`src/data/commands.ts`): SQLite tables `commands` and `command_events` in the service database. Statuses `queued`, `delivering`, `delivered`, `delivery_unknown`, `accepted`, `rejected`, `running`, `completed`, `failed`, with a fixed transition table. Every change appends an event with actor and detail; an actor is at most 256 characters. The recipient may accept or reject while a send is in flight; the sender's report is then appended as an event and the answer stays as the status, so read the status from the command, not from the latest event. Same idempotency key with the same intent returns the original command; with a different intent it is a conflict. On start, a command left in `delivering` becomes `delivery_unknown` (it may have reached the pane), never `queued`; one answered during an unfinished send keeps its status and gets a `delivery_unknown` event.
- **Delivery** (`src/application/delivery.ts`, sender in `src/fleet/sender.ts`): existing `fleet send`, one delivery at a time. The pasted message starts with `Fleet Control command <id> from <actor>:` and says delivery is not approval. Exit 0 with `delivered` is `delivered`. Every unconfirmed result, including `not sent`, `no session`, or a sender crash, is `delivery_unknown` and is not retried automatically. Sender output alone cannot prove that no effect occurred. This changes earlier refusal behavior; existing queued rows are not reclassified and require review before retry.
- **Acceptance and execution are explicit**: `delivered` records the sender’s reported confirmation, not recipient acceptance or execution. The bundled sender checks whether the count of pane lines containing the first 40 characters of the first nonblank line increased; this is a heuristic, not proof that the full message appeared. Only `command_respond` (accepted/rejected) and `command_report` (running/completed/failed with evidence) move it further. Completion before acceptance is refused.
- **MCP** `POST /mcp` (Streamable HTTP, stateless, JSON responses): tools `command_submit`, `command_deliver` (retry a queued one), `command_get`, `command_list` (pages), `command_events` (cursor), `command_respond`, `command_report`. DNS rebinding protection admits only `127.0.0.1:<port>` and `localhost:<port>` Host headers; a browser Origin from elsewhere gets 403.
- **REST** for the web UI, same queue: `GET/POST /api/commands`, `GET /api/commands/:id`. POST is same-origin only; 400 bad input or JSON, 409 key conflict, 404 unknown id. The page does not use it yet.
- `index.ts` and `scripts/dev-test-fleet.ts` wire the queue; `FLEET_CONTROL_DB` keeps it across restarts.

Verification (2026-11-09): `bun test` 51 pass / 0 fail, `bun check` clean. Real `fleet send` against the private test session: command id appears in the pane and status is `delivered`; missing session stays `queued` with `no session ...`; dialog-like text stays `queued` with `not sent`. MCP SDK client against the real server: tool list, submit → delivered, retry with the same key does not paste twice, report before accept refused, accept → completed, REST and MCP see the same command, foreign Host and Origin 403. Negative controls: disabling the intent check fails the conflict test; reconciling to `queued` fails the restart test. ## Implemented locally: stage 5, scoped requests and the page panel (2026-11-09, same branch, tested on 192.168.50.4)

- `src/data/requests.ts`: `Requests` with tables `runs`, `requests`, `request_events`. A run has one orchestrator, the only actor allowed to write its phase record (`registerRun`, `updatePhase` with `expectedRevision`). A request is bound to run, phase and revision. A new revision, or a phase change, makes every open request stale. `resolve` needs the request's revision and an allowed response; a second, different answer is a visible conflict and the first stands; a replay must match the response, normalized actor, request revision and note (omitted and empty notes are equivalent). ## Terminal input lease (2026-11-20, branch `feat/input-lease`, not released)

An operator can type into a session from the page, one writer per session, through a lease bound to one terminal socket. Off unless the host service starts with `FLEET_CONTROL_INPUT=1` and has a tokens file. Design: [input-lease-design.md](input-lease-design.md).

- **Host service.** Each terminal socket gets an id, sent as the first text frame (`{type:"socket"}`); terminal output stays binary. `POST /api/sessions/:name/lease` with `{socket, minutes?, reason?}` grants a lease to that socket if it is the caller's own open terminal of that session, the caller's role has `input` (only `operator`), and no other lease is live (409 names the holder and expiry). `DELETE` ends it (a different operator's DELETE records "revoked by X: reason"). Both need the same Origin. `GET /api/leases` lists live ones, for callers with `input` only. Code: `src/domain/leases.ts`, `src/data/leases.ts` (tables `input_leases`, one live per session by a partial unique index, and `lease_events`), `src/application/leases.ts`, `src/fleet/lease-terminal.ts`, routes and socket handling in `src/server.ts`.
- **Typing.** Binary messages from the holder's socket, at most 4096 bytes each, are pasted with `tmux load-buffer` + `paste-buffer -d` on the fleet's tmux socket, with `-S` where `tmux list-commands paste-buffer` lists it (newer tmux escapes control bytes without it). `send-keys` is refused by tmux while the read-only viewer is attached. tmux is looked up on PATH, then `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin`; without it, `FLEET_CONTROL_INPUT=1` stops the service at start with "FLEET_CONTROL_INPUT: ...". A failed `-S` probe is asked again on the next paste. Text frames are never keys: any text frame from a page closes its socket with 1008. `lease_events` keeps the byte count and SHA-256 of each message, never the text. A message from any other socket, or after the lease ended, closes that socket with 1008 "read-only terminal: no input lease for this socket" and types nothing.
- **A lease ends** when its socket closes, after its minutes (default 5, at most 30), when the agent in the pane exits and leaves it at a shell prompt (the pane ran something else at grant and now runs `sh`, `bash`, `zsh` or a similar shell; a pane that was a shell at grant stays leased while the holder runs commands in it), when the session's tmux id, creation time or active pane pid changes (one `tmux list-sessions` call filtered to the exact session name; agent-fleet restarts an agent in a new window, which changes it; a command typed in the pane does not; an agent restarted by hand in the same pane keeps the lease), on DELETE, and for all leases when the service starts. A 1 s sweep catches expiry, restarts and leases whose socket is gone while nobody types. The LAN and tailnet listeners of one service share one list of open sockets, so a lease taken on one is not swept by the other. A socket that closes while its grant is in flight gets no lease. When tmux cannot be asked (not running is different: that ends the lease as "session ended"), no lease ends on that; queued commands stay held and keys are refused with the error. Expiry needs no tmux. The socket gets `{type:"lease", state:"ended", reason}`. A reconnect never inherits a lease.
- **Queued commands wait.** While a session has a live lease, `fleet send` deliveries to it stay `queued` (shown as queued; there is no separate "waiting for the lease" state); when the lease ends they go out, each on its own, so one failure does not hold back the rest.
- **Gateway.** Forwards the lease routes and binary socket messages up to 4096 bytes; a text message from the page still closes the socket. A DELETE needs no content type (the page sends none) and is refused if it carries a body. The host decides who may type.
- **Page.** Each pane footer has a "Type…" button once the host names the socket. The first click asks for confirmation ("Confirm: type into <session> for 5 min", lapses after 8 s); the second asks the host. Keys are sent only after the host grants, as binary frames; the pane gets an accent outline and a minutes-left status. Any end, refusal or reconnect turns keys off again.

## Orchestrator agents for phased runs (2026-11-20, branch `feat/agent-orchestrator`, not released)

## Adding a host from the gateway (2026-11-20, branch `feat/add-host`, not released)

- The MacBook gateway (`client.ts`) gets an add-host page at `/add-host` and an API at `/api/enroll`, both only with `FLEET_CONTROL_ENROLL=1`. Writes need the page's own Origin, like the installer. The sidebar links to it when the gateway offers it. With the flag on, the gateway also starts from an empty config (`{"hosts": []}`) and the page says "No hosts yet. Use Add a host at the bottom of the host list."; without the flag an empty list stays a config error (2026-11-21, branch `feat/empty-gateway`).
- Steps are kept apart. The gateway makes the token and keeps it in a new `token-<id>` file (0600, never overwrites) next to its config. The page shows one command that carries only the token's SHA-256 hash. The operator runs it on the host, or presses "Run over SSH" (BatchMode, strict host keys, the operator's own SSH setup; nothing new is stored). Check calls the host's `/api/whoami` over verified TLS with the new token, and the gateway adds the host (memory and config file, atomic, mode kept) only when the host answers with tokens on, this principal and the `operator` role. Cancel removes the token file; if the command already ran, the name must be revoked on the host by hand.
- `bun scripts/enroll.ts connect` (run in the folder of a running launchd or systemd --user service) adds the hash line to that service's tokens file under the tokens lock and sends SIGHUP. Pasting it twice changes nothing; a second hash for the same name is refused. `bun scripts/enroll.ts fresh` (run in a fresh clone, which the shown command makes) writes an empty fleet with its own tmux socket, a one-line tokens file and a new launchd or systemd --user service on `127.0.0.1:<port>` plus the Tailscale address. It refuses an existing folder, unit, unreadable certificate or a port below 1024 before writing anything. It does not make the Tailscale certificate: that needs `sudo tailscale cert` on the host.
- Limits: the repository is private, so a fresh clone needs the host's own GitHub access. Hosts being added live in the gateway's memory; a gateway restart forgets them. Their token files stay, and a retry with the same id answers 409 naming the file to remove. Connect needs a host release that has `scripts/enroll.ts`: no released build has it yet (608f243 does not), so .4 and .15 must be updated before connect works there; on an older release the pasted command prints that and changes nothing. ## Managed Claude Code agents (2026-11-19, PR #190, released as `65f608c` on .4 and .15)

With `FLEET_CONTROL_AGENT_ROOTS` set, an operator starts and stops Claude Code agents from the supervisor panel or `POST /api/agents` and `POST /api/agents/<name>/stop` (also through the gateway). The owner chose unattended agents (`--dangerously-skip-permissions`) limited to allowed folders (`~/fleet-agents` on both hosts), models `sonnet`, `opus`, `haiku`, an `autonomy.txt` with hard limits, the operator role and typing the name again to confirm.

- Names are `fc-` plus lowercase letters, digits and dashes, so they never collide with sessions in `fleet.conf`. Each agent is one `AGENTS+=` row and one branch of an `agent_overrides` function (its folder and model) in `fleet-control-agents.conf`. agent-fleet 0.5.0 (PR #12) calls `agent_overrides` with the session name on every start and replacement, so a replaced or recreated agent keeps its folder and flags. The service refuses to start an agent when `$FLEET_DIR/watchdog.sh` does not know `agent_overrides` (an older watchdog would start Claude Code in the fleet's default folder with the fleet's default arguments), and when `FLEET_CONF` is not `$FLEET_DIR/fleet.conf` (agent-fleet would never read the include). Only `starting` and `running` agents keep a row, and the rows are read from the database when the file is written, so a start that waited behind a stop does not write the stopped agent back. A watchdog that is already running keeps the agent list it read at its start: it recreates a stopped or failed agent until it is restarted. No watchdog runs on .4 or .15 now. The prompt is stored as a 0600 file in `FLEET_DIR`; agent-fleet 0.5.0 writes its start and replacement copies 0600 and recreates older ones; the database keeps only its SHA-256 and size. A prompt with a live access token is refused.
- States: `starting`, `running`, `failed` (with the start or stop error), `stopping`, `stopped`. A live row is never replaced; a failed or stopped name can be started again. Stop kills only that tmux session and drops its row; any state but `stopped` can be stopped, including a `stopping` row left by an interrupted stop. When the service starts it settles rows a restart cut off: `starting` becomes `running` if its session is open, otherwise `failed`; `stopping` becomes `stopped` if the session is gone, otherwise `failed` ("stop it again"). An agent stopped while still starting is stopped again once its launch ends.
- `fleet start` runs outside the lock that guards the fleet files, so a stop does not wait up to 150 s behind another agent's start. The folder is marked trusted in `~/.claude.json` before any other file is written, under a lock directory (`~/.claude.json.fleet-control.lock`), through a symlink if there is one, and not rewritten when it is already trusted. An unreadable state file stops the start with nothing written.
- `serve()` refuses managed agents without tokens, even on loopback. The gateway relays agent calls with its own per-host token, which must be `operator`; anything that can reach the loopback gateway can then start an agent, as it can already queue commands. Treat the gateway as a privileged local surface. Cooperative (central) hosts have no agent routes; the page hides the box for them.

## Not implemented in this project

- A service on `.4` for real fleets. The installed one serves only the test fleet `fctrl-test`. This project installed no host service on `.15`.
- Using the viewer with real agent sessions: the agent-fleet `send-keys` bug ([bugs/agent-fleet-send-keys-read-only-viewer.md](bugs/agent-fleet-send-keys-read-only-viewer.md)) is fixed in the pinned `vendor/agent-fleet` (see the 2026-11-11 correction above), and a real Claude Code agent received the pasted Enter with the viewer open (2026-11-12, private fleet), and the installed `.4` service runs that CLI since the 2026-11-15 upgrade; real-session use still needs the owner's authorization.
- phased-delivery writing its phase record and requests through the MCP tools; a real orchestrator using them. `scripts/run-file-sync.ts` can mirror a `run.md` phase table into the run record (tested against a local service only); the skill does not call it.
- Terminal input and exclusive input leases. The viewer is read-only by design.
- Push event stream (the page polls every 3 s for requests and commands, 15 s for sessions, only while its tab is visible; showing the tab refreshes at once. A tab hidden for a minute closes its terminal viewers and reattaches when shown).
- Model observers for harnesses other than Claude Code, and for remote (`REMOTE_SSH`) fleets, which each host's own service should observe.
- Supervisor replacement, reboot recovery of in-flight commands beyond `delivering` → `delivery_unknown`, event retention, and scheduled backups. A manual backup (`scripts/host-backup.ts`) and a read-only restore check of it (`scripts/host-restore-check.ts`) exist; neither is scheduled, and no restore onto a host has been run.
- Finer permissions than the three roles (an agent can do every write except answer a request or write another orchestrator's phase). Tokens are added, rotated, revoked and given a role with `scripts/tokens.ts` (checked, atomic, 0600); the service rereads the file on SIGHUP and keeps the old tokens if the new file is invalid (released hosts before this change need a restart). There is no expiry or overlap window for a rotated token.

The mockup's send button writes only browser memory. The live page (`web/`) posts to the service.

## Open decisions
