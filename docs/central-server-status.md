# Central backend status

The central backend is a local prototype, **not production ready**. This page describes the code in `src/central/`, `src/host-agent/` and `scripts/central-backup.ts`, not a deployed service or an end-to-end agent integration. Source inspection is not evidence of a production deployment or a live-agent test.

## Current implementation

- `bun src/central/main.ts` starts a Bun HTTP server bound only to `127.0.0.1`. Startup reads a credentials file, opens a PostgreSQL connection and initializes the command, request and supervisor identity tables. It requires every configured supervisor identity to be enrolled and active before listening. It does not start delivery recovery.
- Bearer tokens are checked against SHA-256 hashes in the credentials file. Principals have operator, host or supervisor roles. The command REST API is operator-only; `/mcp` is available to operators and supervisors. Supervisors' command access is scoped to their configured host and session. The server rejects an Origin header unless it is explicitly allowed; the entry point does not configure allowed origins.
- The operator REST API can submit, list and read commands. The MCP tools support command submission and scoped reads, plus supervisor responses and execution reports. A submission creates a PostgreSQL `queued` record and event; matching idempotent submissions return the existing command, while changed intent conflicts. Queued, delivered, accepted and completed are distinct states. Supervisors may also accept or reject a queued command directly, so acceptance is not proof of transport delivery.
- PostgreSQL-backed runs, phase revisions, requests and events are exposed through MCP. An operator can relay a response; the owning supervisor can manage a run and check its approval gate. A changed phase or revision makes open requests stale. Acknowledging an answer does not start a phase.
- The entry point mounts an authenticated, inventory-only host WebSocket at `/api/host/socket`. It rejects browser Origin headers and receipts. Operator-only `GET /api/hosts` returns process-local observations of accepted authenticated sockets as `{ hostId, sessions }`: `sessions` is `null` until valid inventory arrives, then contains the host's self-reported session names. Entries are removed on disconnect; state is lost on server restart. There is no heartbeat or freshness guarantee, so a listed socket is not proof that a host or session is healthy or available. The separate host client can publish inventory on connection and reconnect, but it is not integrated into a running host-agent runtime. Dispatch remains disabled. Separate modules implement delivery attempts, a host WebSocket client, and a SQLite host journal and executor. These are building blocks, not an integrated runtime. The journal records an attempt before sending and maps an interrupted `started` attempt to `unknown` when its explicit recovery method is called. The executor checks a supplied runtime instance ID before sending.
- A standalone SQLite receipt outbox stores `delivered` or `unknown` receipts keyed by attempt ID, rejects conflicting duplicates, lists pending receipts and retains acknowledged records for deduplication. It is not wired into the journal, executor or host client. The client sends a receipt only while its original socket remains connected; there is no outbox replay or central acknowledgement protocol.

## Standalone cooperative HTTP prototype

`src/central/cooperative-server.ts` exports `createCooperativeCentralApp`, a separate dependency-injected HTTP app. It is not started or mounted by `src/central/main.ts`; that entry point still starts the legacy central app described above. A caller must initialize and supply its stores, authentication and identity lookup, arrange a listener and provision incarnation credentials. No installed adapter or running agent integration is established by this code.

The cooperative app provides operator-only command submission, `GET /api/commands/:id/cooperative`, and, when the reconciliation store is supplied, `GET /api/commands/:id/cooperative/assertions`, plus an authenticated `/mcp`. Operators receive the existing central MCP tools; supervisors receive only `cooperative_claim` and `cooperative_report`, not legacy supervisor mutation tools. Each supervisor HTTP request rechecks its active identity, and MCP requires incarnation ID and token headers. Header shape is checked at the HTTP boundary; the stores validate the credential and active incarnation during each claim or report. Unknown origins are rejected unless explicitly allowed. The standalone app has no host socket or automatic incarnation activation.

Operator inspection returns the command, optional claim metadata, paginated cooperative lifecycle events and `nextCursor`. The default event page is 100, maximum 1,000; its sequence cursor supports subsequent live reads, not a snapshot across pages. The command row remains `claimed` even when lifecycle reports show completion. The endpoint does not provide reconciliation assertions or imply execution occurred.

`src/central/incarnations.ts` and `src/central/cooperative-claims.ts` provide the underlying stores. Activation is a trusted operation for an enrolled active identity; it replaces active incarnations for the same host and session. The database stores a hash of the generated token. Claim transactions check and lock the slot, identity and active incarnation, then serialize on the command event lock. Replacement or retirement prevents later claims with the old credential; a claim that acquired its locks first can commit before either operation. This does not cancel already claimed work or fence external effects.

A claim selects a queued command for the identity's host and session only if it has no delivery attempt or previous claim. It records the `claimed` status and event atomically. The request ID is scoped to the incarnation and persists even for an empty result, so repeating that request returns the same command or empty result. A claim is a reservation, not acceptance, delivery or execution. `claimed` is readable through the current central REST and MCP status filters and the shared host command store, but legacy transition rules cannot enter or leave it. The shared host status type and reader support do not wire the host service into cooperative claims.

The claim initializer uses `current_schema()` to schema-qualify its claim table, trigger function, command table and trigger function's claim lookup. The trigger blocks all updates and deletes of a claimed command. This avoids a trigger lookup drifting to another schema, but does not make initialization or runtime generally search-path safe: other initializers and operational queries use unqualified names. The initializer itself says its lock does not coordinate concurrent initialization or installation. Use a dedicated database/schema and controlled, consistent search paths; do not run initialization concurrently or assume it repairs existing objects or removes triggers in other schemas. Claimed rows are frozen, not external effects or arbitrary database writes. Privileged SQL, nonparticipating writers and unsafe restores can invalidate the protocol.

`src/central/cooperative-lifecycle.ts` records reports in `central_cooperative_lifecycle_events`, not the normal command event table, and leaves the command row frozen as `claimed`. It checks the supervisor identity and active incarnation, requires that incarnation to own the claim, and uses an incarnation-scoped request ID to deduplicate identical reports and reject conflicting reuse. Its allowed transitions are `claimed` to `accepted` or `rejected`, `accepted` to `running`, `completed` or `failed`, and `running` to `completed` or `failed`. These reports are visible through cooperative inspection, not normal command status or event reads. The legacy entry point does not initialize or expose this store; there is no integrated release, retry or recovery path.

`src/central/cooperative-mcp.ts` implements the cooperative tools used by the standalone app. It takes an authenticated supervisor principal and out-of-band incarnation credential, validates their shape, copies them into its closure and delegates to the stores. The standalone HTTP app supplies authentication and transport, but does not provision credentials. The MCP module sanitizes errors and rejects inputs or serialized responses containing the exact incarnation token; this is not general secret redaction. The adapter also rejects responses containing its local bearer, supervisor bearer or incarnation ID, but the central pre-commit claim guard does not check all of those values. A command containing one can therefore be claimed while its response is rejected; exact retries can remain unreadable. This cross-layer failure was reproduced with a synthetic store; its PostgreSQL consequence follows from source inspection, not a database reproduction. Do not automatically requeue such a claim. Do not mount legacy supervisor mutation routes alongside it. The legacy entry point mounts neither the cooperative app nor its stores.

`src/central/cooperative-reconciliation.ts` is a separate trusted-operator assertion store; only its read operation is mounted by the disposable cooperative app. It records disposition and evidence against a claim. A new assertion compares both the latest lifecycle sequence and latest assertion sequence under the event lock, then appends a sequenced assertion; identical request-ID retries return the original, conflicting reuse fails. This compare-and-set detects stale evidence or competing assertions, but changes neither claim nor lifecycle nor execution. `reconcile` accepts an optional transaction runner; initialization still requires trusted DDL, and the disposable runtime role cannot write the assertion table. Its operator-authorized store-level `list` reads a claim’s assertions in ascending numeric sequence, defaulting to 100 and capped at 1,000 per page. A missing claim (including a missing command) returns null; an existing claim with no matching assertions returns an empty page. Sequence and cursor values remain decimal strings, and pagination is live rather than a snapshot. The optional transaction runner also wraps reads. The disposable cooperative app mounts operator-only `GET /api/commands/:id/cooperative/assertions` using the guarded runner; the runtime role receives only SELECT on the assertion table. Missing claims return 404 and existing claims without assertions return an empty page. The route defaults to and caps pages at four assertions, accepts a decimal cursor of at most 1,000 digits, and uses live pagination. The bounded read checks the combined byte length of each returned row and the lookahead row in one SQL statement; an oversized row fails the page rather than sending its fields to the app. Serialized JSON is capped at 2 MiB, including its envelope; oversized pages return a generic error. This limits returned data, not PostgreSQL physical I/O, sorting or decompression. Privileged writers can still invalidate stored data. It is not claim recovery, release or retry.

## Standalone adapter, fresh provisioner and schema guard

These modules remain separate from `src/central/main.ts`, `index.ts` and `client.ts`. The disposable adapter process described below starts the adapter and listener, but does not install or start an agent or change any deployed service.

- **Host-side adapter** (`src/host-agent/cooperative-adapter.ts`): `createCooperativeAdapter` returns an in-memory `(request) => Promise<Response>` handler. It is not a listener, process or deployment. It requires a central URL that is `https` with the exact path `/mcp` (loopback `http` only with the test-only `allowLoopbackHttpForTests`), a 43-character base64url local token, and a supervisor token, incarnation ID and incarnation token that are all distinct. A local caller must present the local token. The adapter accepts only `POST /mcp` JSON-RPC bodies without an Origin header and forwards them to the fixed central endpoint, adding the supervisor bearer and the incarnation ID and token headers itself. It caps requests at 512 KiB and responses at 2 MiB, defaults to a 30 s timeout and 16 concurrent requests, and rejects input containing any configured secret. If a request was forwarded and the response is lost or unusable, the adapter reports the outcome as unknown with no automatic retry; only an exact manual retry of the same request ID and payload with the same incarnation is safe. Any process under the same UID may read adapter memory or obtain the local token, so the agent must be trusted; the tokens are not a defense against a hostile same-UID process.
- **Loopback listener** (`src/host-agent/cooperative-listener.ts`): `createCooperativeListener({ handler, port })` binds `127.0.0.1` (port `0` unless given), rejects any Origin header and any Host header other than `127.0.0.1:<port>` or `localhost:<port>`, and leaves authentication to the handler. `stop()` stops accepting new work and waits up to five seconds for connections and accepted handler promises, then force-closes connections. Handler or upstream work may continue after the deadline; its outcome can be unknown. The disposable adapter process starts it.
- **Fresh provisioner** (`src/central/cooperative-provision.ts`): `provisionCooperative(db, options)` is trusted administration for a disposable local database. In one transaction, under an advisory lock, it creates a new schema (default `fleet_cooperative_v1`) with the command, delivery, identity, incarnation, claim, lifecycle, reconciliation, run and request tables, schema-qualified claim and reconciliation triggers, and a `central_cooperative_schema_marker` row. It fails if the schema already exists, so it neither upgrades nor repairs an existing installation, and it is not a migration of the legacy tables. A test schema must match `cooperative_test_<32 hex>`. The marker records that installation ran, not the integrity of the objects. The disposable cooperative central entry point calls it.
- **Schema guard** (`src/central/schema-guard.ts`): `withCooperativeSchema(db, schema, operation)` validates the identifier, then in one transaction requires a role that is not superuser, does not bypass row security, is not a member of the schema owner role and has no `CREATE` on the schema. It sets a transaction-local `search_path` of `pg_catalog,"<schema>",pg_temp` and requires exactly one marker row with version `fleet_cooperative_v1`. It checks only the role, the search path and the marker, not schema integrity or every privilege. The disposable cooperative entry point injects this guard into the store operations it exposes. Other store methods and callers may still use the connection's own search path; the guard is not a blanket guarantee for the standalone app or all public methods. In particular, legacy `CentralCommands` transitions, scoped reads, event reads and restart reconciliation do not use the injected runner and must not be exposed with this runtime pool.

`src/host-agent/cooperative-main.ts` is a separate disposable loopback adapter process. Set `COOPERATIVE_ADAPTER_CONFIG_FILE` to an absolute path to a private, current-user-owned regular JSON file with exactly `centralUrl`, `localToken`, `supervisorToken` and `incarnationFile`. The incarnation file must also be private and current-user-owned and contain exactly `incarnationId` and `token`. Final-component symlinks are refused. The central URL must use a numeric loopback host and `/mcp`; HTTP is allowed only for this disposable experiment. Both bearer tokens and the incarnation token must meet the adapter requirements and be distinct. It binds an ephemeral port on 127.0.0.1 and prints only its URL. Same-UID processes remain trusted. SIGINT or SIGTERM stops accepting requests, waits up to five seconds for connections and accepted handler promises, then force-closes the listener. It does not cancel in-flight upstream work: a request can complete after shutdown with its result unknown. Never automatically retry or requeue; only retry the exact request ID and payload with the same incarnation.

`src/central/cooperative-main.ts` is a separate disposable-experiment entry point. It refuses any database other than `127.0.0.1:57507/fleet_control_test`, provisions a new `cooperative_test_<32 hex>` schema on every start, enrolls and activates the single configured supervisor, and serves the cooperative app on loopback. It writes the incarnation ID and token to `COOPERATIVE_INCARNATION_FILE`, which must be an absolute path that does not exist, using exclusive create with mode `0600`; stdout shows only the URL and incarnation ID. It provisions with the trusted `COOPERATIVE_DATABASE_URL`, then connects using `COOPERATIVE_RUNTIME_DATABASE_URL`, a pre-created restricted login named `cooperative_runtime_<32 hex>` on the same fixed test database. The provisioner grants that login access to the new schema. Startup and exposed cooperative store operations use the schema guard in their own transactions. It does not start a host agent, recover, or drop schemas. Its loopback PostgreSQL test covers submit, claim, accepted and completed reports, and operator inspection with a synthetic client, not a real agent.

A local real-agent smoke attempt initialized MCP and discovered both cooperative tools, but the agent invoked neither; operator inspection showed the command still queued without a claim or lifecycle events. The attempt did not retain its error. A separate Claude Code diagnostic reported that it was not logged in; the cause of the smoke failure is unconfirmed. The owner declined further Claude use. Real-agent integration is not verified. The separate-process test is synthetic and uses a restricted database role with the schema guard. The guard does not protect external effects, verify schema integrity, or prevent trusted privileged writers from bypassing the protocol.

`transitionScoped` and optional request-store mutation guards provide transaction-bound hooks, but the server and MCP handlers do not wire them to incarnation validation. Existing supervisor routes therefore do not gain incarnation fencing from these methods. Old deployed readers may not understand `claimed`; old writers and delivery workers may bypass the cooperative locking contract. Any eventual cutover must account for all readers and writers and needs a reviewed, tested compatibility and recovery design. There is no safe production migration procedure here; do not enable the prototype or remove its fence as a production cutover.

## Limits and safety

- **No real agent dispatch:** the mounted socket is inventory-only; the entry point does not wire delivery attempts or start a host-agent process. The dispatch message has no runtime instance ID, although the separate executor requires one. Do not treat the isolated components as an end-to-end delivery path.
- **Identity enrollment is trusted, not runtime fencing:** supervisor run ownership uses the configured name, `principalId`, host ID and session together. Startup requires an exact active PostgreSQL registry binding, and each authenticated supervisor HTTP request rechecks it, failing closed on a mismatch or lookup error. Enrollment is an explicit trusted operator action; existing credentials are not automatically migrated. An ID cannot be rebound or re-enrolled after retirement while its registry record is retained. This does not establish a runtime-incarnation fence: command scope remains host and session name, and the registry can be bypassed or lost by someone with database write access or an unsafe restore. Revocation does not retroactively cancel a request already in progress.
- **Pagination is not a snapshot:** REST `GET /api/commands` and MCP `command_list` and `request_list` expose `limit`, `cursor` and `nextCursor`. Pages default to 100 records and allow 1 to 1,000, ordered by creation time and ID. Clients should retain the same filters while traversing. The keyset traversal does not hold a snapshot: concurrent inserts or status changes can cause records to be missed. The request gate uses a separate query. Run lists and event queries remain unbounded; event queries accept `afterSeq` but have no result limit. `request_list` also returns the unbounded run list on each page.
- **Cursor scope:** command and request cursors include their filters, but are not signed and must not be treated as authorization. Neither API provides snapshot isolation.
- **The phase gate is informational, not authorization:** `request_gate` reports the approval state for a phase and revision. It does not prevent the supervisor from updating the phase or performing work, and acknowledgement does not start a phase.
- **Recovery is not automatic:** methods exist to mark interrupted central delivery as unknown, but startup does not call them. Their documented precondition is that previous delivery workers have stopped. The host journal has its own explicit recovery method. None of this establishes a safe coordinated restart or retry protocol.
- **No safe restore procedure is implemented or verified.** `scripts/central-backup.ts` invokes `pg_dump` in custom format with TLS `verify-full`, requires an explicit PostgreSQL URL and a new output path, and leaves an incomplete file on failure. It does not validate an archive against its source, create a second copy, restore it, or reconcile it with host journals. A dump file alone is not a verified backup.
- The server binds to loopback and does not provide TLS through this entry point. The mounted inventory socket does not establish a connected host-agent runtime. There is no production deployment, complete authentication lifecycle, restore workflow or live-agent operation established by these files. Parallel implementation is unsettled; this page describes only the local source inspected and should be rechecked before relying on it.

## Local configuration

For an isolated local experiment, provide `CENTRAL_DATABASE_URL` for a PostgreSQL database and `CENTRAL_CREDENTIALS_FILE` for a readable JSON file outside the repository. `CENTRAL_PORT` is optional and defaults to `4872`; if set it must be between 1 and 65535. `CENTRAL_HOST`, if set, must be exactly `127.0.0.1`. Start with `bun src/central/main.ts`. Startup creates tables in the configured database, so use a dedicated local database, not production data.

The credentials file is a nonempty JSON array of objects with `tokenHash` and `principal`. `tokenHash` is a lowercase SHA-256 hex digest of the bearer token, not the token itself. A principal has `name` and `role`; a `host` also needs `hostId`, and a `supervisor` needs `principalId`, `hostId` and `session`. Names, token hashes and supervisor principal IDs must be unique within the file. Before startup, a trusted operator must enroll each supervisor tuple in the same database, for example with `DATABASE_URL` set outside the command line: `bun src/central/identity-cli.ts enroll --principal-id ID --name NAME --host-id HOST --session SESSION`. Use `retire` with the same flags to retire a binding. The CLI initializes the registry table and has no automatic migration or credential-file update. Retired configured supervisors prevent the next startup until credentials are updated. Keep the file, tokens and database URL private; do not commit secrets. Credentials are loaded at startup.

## Tests and legacy service

Run the focused tests with `bun test src/central src/host-agent scripts/central-backup.test.ts`. PostgreSQL integration tests are skipped without `CENTRAL_TEST_DATABASE_URL`; the legacy loopback integration test requires a disposable local database named `fleet_control_test` on `127.0.0.1`. Use only a dedicated disposable test database, since tests initialize and write database objects. The cooperative loopback test assembles the standalone app and stores in a random schema, exercises synthetic submission, claim, reports, inspection and replacement fencing, and drops that schema afterward. It is not a running agent integration. Cooperative-claim tests also isolate their search paths and check the trigger schema. They do not remove a pre-existing trigger in `public`. A public trigger was reported in the disposable test database; its current presence has not been checked in this documentation pass. It is outside isolated test cleanup and can affect other tests using public tables. Do not infer its absence or removal from these tests. A skipped integration test is not a pass against PostgreSQL.

`src/central/cooperative-process.test.ts` starts separate central and adapter processes against the disposable local PostgreSQL fixture, with separate provisioning and restricted runtime roles. It checks synthetic submission, claim and exact replay, accepted and completed reports, inspection and stale-incarnation claim and nonterminal report rejection. It does not run an agent or execute commands. The adapter and listener also have mock-fetch and loopback unit tests with no database. `src/central/cooperative-adapter-integration.test.ts` runs the adapter against the standalone app and stores in a random schema over loopback HTTP, with synthetic commands and the test-only HTTP allowance. `src/central/cooperative-provision.test.ts` (fresh install, concurrent install with one winner, rollback on injected failure, no change to a sentinel schema, use by the cooperative stores) and the database part of `src/central/schema-guard.test.ts` (unsafe roles, schema ownership, marker checks, search-path pinning) run only when `CENTRAL_TEST_DATABASE_URL` is set, and both refuse anything but the disposable `postgres://…@127.0.0.1:57507/fleet_control_test` database. Only the identifier-rejection test of the guard runs without a database.

Last full run in this checkout (2026-11-11), with `CENTRAL_TEST_DATABASE_URL` pointing at the disposable loopback PostgreSQL fixture: `bun test` reported 348 pass, 0 fail and 3,443 assertions across 63 files; `bun run typecheck` passed in 119 files. This includes the separate-process synthetic cooperative test and PostgreSQL-backed schema guard tests, not a live agent or production environment.

This central prototype does not replace them or establish that any existing deployment was changed.
