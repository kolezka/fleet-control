# Central backend status

The central backend is a local prototype, **not production ready**. This page describes the code in `src/central/`, `src/host-agent/` and `scripts/central-backup.ts`, not a deployed service or an end-to-end agent integration. Source inspection is not evidence of a production deployment or a live-agent test.

## Current implementation

- `bun src/central/main.ts` starts a Bun HTTP server bound only to `127.0.0.1`. Startup reads a credentials file, opens a PostgreSQL connection and initializes the command, request and supervisor identity tables. It requires every configured supervisor identity to be enrolled and active before listening. It does not start delivery recovery.
- Bearer tokens are checked against SHA-256 hashes in the credentials file. Principals have operator, host or supervisor roles. The command REST API is operator-only; `/mcp` is available to operators and supervisors. Supervisors' command access is scoped to their configured host and session. The server rejects an Origin header unless it is explicitly allowed; the entry point does not configure allowed origins.
- The operator REST API can submit, list and read commands. The MCP tools support command submission and scoped reads, plus supervisor responses and execution reports. A submission creates a PostgreSQL `queued` record and event; matching idempotent submissions return the existing command, while changed intent conflicts. Queued, delivered, accepted and completed are distinct states. Supervisors may also accept or reject a queued command directly, so acceptance is not proof of transport delivery.
- PostgreSQL-backed runs, phase revisions, requests and events are exposed through MCP. An operator can relay a response; the owning supervisor can manage a run and check its approval gate. A changed phase or revision makes open requests stale. Acknowledging an answer does not start a phase.
- The entry point mounts an authenticated, inventory-only host WebSocket at `/api/host/socket`. It rejects browser Origin headers and receipts. Operator-only `GET /api/hosts` returns process-local observations of accepted authenticated sockets as `{ hostId, sessions }`: `sessions` is `null` until valid inventory arrives, then contains the host's self-reported session names. Entries are removed on disconnect; state is lost on server restart. There is no heartbeat or freshness guarantee, so a listed socket is not proof that a host or session is healthy or available. Inventory session names with malformed UTF-16 are rejected: the server closes the socket and removes its inventory, while the host client rejects them before sending. Well-formed Unicode remains accepted. The optional asynchronous inventory callback can complete out of order or after disconnect; consumers must not assume it receives a serialized current-state stream. The mounted callback is currently a synchronous no-op. The separate host client can publish inventory on connection and reconnect, but it is not integrated into a running host-agent runtime. Dispatch remains disabled. Separate modules implement delivery attempts, a host WebSocket client, and a SQLite host journal and executor. These are building blocks, not an integrated runtime. The journal records an attempt before sending and maps an interrupted `started` attempt to `unknown` when its explicit recovery method is called. `openExclusiveJournal` (`src/host-agent/executor-lease.ts`) holds a cross-process SQLite lock before that recovery and the journal refuses writes once the lock is released; it is cooperative, does not cover hard-linked paths, and no runtime uses it yet. Journal access rejects malformed UTF-16 attempt IDs and fingerprints; previously an invalid ID could alias a replacement-character ID and change its outcome. Existing normalized records are not repaired, and an invalid retry does not prove no earlier attempt occurred. The executor rejects malformed UTF-16 in all offer fields before journal lookup or sending, and checks a supplied runtime instance ID before sending. This also rejects exact retries of historical malformed offers rather than returning their recorded attempt; invalid IDs now raise a generic offer error instead of JournalError. The existing journal row is unchanged, and rejection does not prove no earlier send occurred.
- The host client calls its `onError` observer inside a guard. Previously, if execution failed and the observer also threw, the dispatch promise queue stayed rejected: later dispatches never ran and their pending count was never released. Now an exception thrown by the observer is caught and replaced by one fixed `console.error` line that omits the raw errors, and the queue continues as it already did when the observer returned normally. The same guard means a throwing observer no longer skips the reconnect after a socket factory failure, and no longer escapes the socket error listener. The observer still receives raw errors. Synthetic-socket regressions cover these cases. When the client rejects an invalid dispatch and `socket.close` throws, it now still schedules a reconnect instead of staying disconnected with no retry timer. Dispatch is not integrated into the running server, and other reconnect and cleanup edge cases in the client are unresolved.
- Host socket messages reject lone UTF-16 surrogates in both directions. Central closes the socket with 1008 on a receipt with a malformed id, rejects a malformed connect host id the same way, and throws `TypeError` to the caller of `dispatch()` when an outgoing id, target or text is malformed. The host client closes with 1008 and never executes such a dispatch, and its constructor rejects a malformed host id or token. These inputs were accepted before and could alias a different id after UTF-8 storage.
- A standalone SQLite receipt outbox stores `delivered` or `unknown` receipts keyed by attempt ID, rejects conflicting duplicates, lists pending receipts and retains acknowledged records for deduplication. It rejects malformed UTF-16 receipt IDs and snapshots input fields; malformed inputs previously could alias normalized SQLite values, including acknowledging a different attempt. Existing normalized rows are not repaired, and a rejected retry does not prove an earlier write did not occur. When called inside a caller-owned transaction, successful `enqueue` and `acknowledge` returns do not make their changes durable: an outer rollback can undo both. An in-memory test covers rollback and commit, not disk durability. It is not wired into the journal, executor or host client. The client sends a receipt only while its original socket remains connected; there is no outbox replay or central acknowledgement protocol.

## Unintegrated dispatch snapshot

`AgentSockets.dispatch` now captures each field once and validates the same values it serializes in a canonical object containing exactly `version`, `type`, `hostId`, `commandId`, `attemptId`, `target` and `text`. Extra properties and caller-provided `toJSON` are not serialized, changing behavior for direct callers that relied on them. A registration token fences disconnect and reconnect ABA during dispatch, including reuse of the same socket object. Receipt handling also checks the registration after `validateAttempt` resolves, whether it resolves successfully or false; a fake test covers this fence, not a real WebSocket. The socket adapter uses a per-open generation to prevent a stale rejected inventory callback from closing a successor, including when the socket object is reused. An accepted open captures hostId for subsequent message and close handling rather than rereading mutable socket data. When an open is rejected for an invalid or duplicate host, AgentSockets permanently marks that socket object as closing before attempting to close it. Reentrant or later reuse of that object is rejected without another close attempt, including if close throws. This changes compatibility for direct external callers that reuse rejected socket objects. The evidence for these behaviors is limited to offline fake sockets; it does not prove behavior with an actual Bun WebSocket. Untagged old message or close events on a reused socket cannot be distinguished from events for its current open. Async inventory callback effects and ordering remain unresolved, including callbacks completing after disconnect. Rejections and errors still propagate. Dispatch remains unintegrated; a successful send is not a receipt or proof of real delivery.

## Host client connection fencing

A unique token per connect fences retained listener closures and queued work, including when a socket factory reuses an object. Receipt serialization and the send accessor are checked again before sending on the captured socket. Offline fakes cover duplicate execution, stale queued work, receipt forwarding and reentrant serialization; no real WebSocket behavior is established. Already-started execution cannot be cancelled. Untagged events emitted on a reused socket can still be delivered to its current listener. Later fixes fence some lifecycle paths: each connect allocates a connection token before calling the socket factory, so a factory that stops or restarts the client cannot schedule a stale reconnect or keep an orphan socket; the invalid-dispatch path reconnects only for its own connection; `stop()` detaches the reconnect timer before clearing it. Offline fakes cover these. A throwing `clearTimer` no longer leaves the socket open, and a timer it failed to cancel cannot reconnect or disturb a later retry; a synchronous injected `setTimer` no longer blocks later retries. If listener registration throws, the client drops and closes that socket (unless a newer attempt reinstalled the same object) and retries. Close confirmation remains unresolved. The receipt outbox remains disconnected.

## Host inventory snapshots

The host client captures own indexed session values once, validates the captured array and sends that snapshot. Custom iterators and array serialization hooks no longer alter it. A valid newer attempt supersedes older inventory work even when its frame is oversized or send throws; invalid input does not. A stale public call throws, while a stale provider result is discarded. The inventory provider is now read once asynchronously instead of twice, and provider errors still reach `onError`, even after becoming stale. These are observable compatibility changes. Fake sockets cover the capture and reentrant cases; they do not prove real WebSocket delivery. The implementation assumes trusted built-ins and is not a sandbox against same-process tampering. Untagged stale events and reused socket objects remain unresolved.

## Standalone cooperative HTTP prototype

`src/central/cooperative-server.ts` exports `createCooperativeCentralApp`, a separate dependency-injected HTTP app. It is not started or mounted by `src/central/main.ts`; that entry point still starts the legacy central app described above. A caller must initialize and supply its stores, authentication and identity lookup, arrange a listener and provision incarnation credentials. No installed adapter or running agent integration is established by this code.

Cooperative command submission rejects host IDs that cannot be registered as supervisor identity IDs, including leading or trailing whitespace and control characters. Exact idempotent replay of an existing command is checked before this new validation, so an older matching request can still recover its receipt. This does not verify that a host or session is enrolled or active, so a syntactically valid but unprovisioned target may remain queued. Command targets allow only ASCII letters, digits, dot, underscore and hyphen; the identity registry also accepts some other session names, which cannot be targeted by new commands. Legacy submission is unchanged.

The cooperative app provides operator-only command submission, `GET /api/commands/:id/cooperative`, and, when the reconciliation store is supplied, `GET /api/commands/:id/cooperative/assertions`, when the settlement store is supplied, operator-only `GET` and `POST /api/commands/:id/cooperative/settlement`, plus an authenticated `/mcp`. Operators receive central command MCP tools, but no request tools. The cooperative app intentionally rejects any non-undefined `requests` dependency at startup: this is an API compatibility change for callers that previously supplied a request store. Those tools include unbounded reads and are not uniformly schema-guarded. The legacy central app retains request-store support. Supervisors receive only `cooperative_claim` and `cooperative_report`, not legacy supervisor mutation tools. Each supervisor HTTP request rechecks its active identity, and MCP requires incarnation ID and token headers. Header shape is checked at the HTTP boundary; the stores validate the credential and active incarnation during each claim or report. Unknown origins are rejected unless explicitly allowed. The standalone app has no host socket or automatic incarnation activation.

Operator inspection returns the command, optional claim metadata, paginated cooperative lifecycle events and `nextCursor`. Claim metadata includes `incarnationActive`, read in the same statement: true only while the claiming incarnation is active and its identity is not retired. `false` means nobody can report on the claim any more. It is a read-only signal, not a recovery path. `settled` is true when an operator settlement exists for the claim. The HTTP page defaults to and is capped at four events; clients requesting more receive 400. The separate store-level `inspect` API retains its default of 100 and maximum of 1,000. Pages are live reads, not a snapshot across pages. A single SQL statement checks the combined size of each command, claim and event row, including the lookahead, before sending fields to the app. Oversized rows fail the page; serialized HTTP JSON is capped at 2 MiB. These bounds do not limit PostgreSQL physical I/O, sorting or decompression. The command row remains `claimed` even when lifecycle reports show completion. The endpoint does not provide reconciliation assertions or imply execution occurred.

`src/central/incarnations.ts` and `src/central/cooperative-claims.ts` provide the underlying stores. Activation is a trusted operation for an enrolled active identity; it replaces active incarnations for the same host and session. Identity fields must be well-formed UTF-16 at enrollment, activation and claim fencing; this rejects previously accepted malformed identities and does not repair existing records. The database stores a hash of the generated token. Claim transactions check and lock the slot, identity and active incarnation, then serialize on the command event lock. Replacement or retirement prevents later claims with the old credential; a claim that acquired its locks first can commit before either operation. This does not cancel already claimed work or fence external effects.

Central command and delivery-attempt mutations, cooperative claim and lifecycle writes, and reconciliation writes fail closed when the command event-lock singleton is missing. Claim and reconciliation trigger initialization also checks the lock before replacing triggers; reconciliation initialization may already have created its table and function. This changes behavior for incomplete schemas and does not repair them. Offline transaction fakes cover the checks but do not prove PostgreSQL lock contention or rollback. Central command submission rejects malformed UTF-16 and NUL characters in all input fields before opening its transaction, including through the legacy store API. This changes previously accepted inputs and does not repair existing commands. A claim selects a queued command for the identity's host and session only if it has no delivery attempt or previous claim. It records the `claimed` status and event atomically. The request ID is scoped to the incarnation and persists even for an empty result, so an exact repeat by the same still-active incarnation refers to that recorded command or empty result; an adapter can still reject the response. An empty replay does not poll for new work. Claim request IDs with malformed UTF-16 are rejected before writes; this changes previously accepted input and does not repair existing records. A claim is a reservation, not acceptance, delivery or execution. `claimed` is readable through the current central REST and MCP status filters and the shared host command store, but legacy transition rules cannot enter or leave it. The shared host status type and reader support do not wire the host service into cooperative claims.

The claim initializer uses `current_schema()` to schema-qualify its claim table, trigger function, command table and trigger function's claim lookup. The trigger blocks all updates and deletes of a claimed command. This avoids a trigger lookup drifting to another schema, but does not make initialization or runtime generally search-path safe: other initializers and operational queries use unqualified names. The initializer itself says its lock does not coordinate concurrent initialization or installation. Use a dedicated database/schema and controlled, consistent search paths; do not run initialization concurrently or assume it repairs existing objects or removes triggers in other schemas. Claimed rows are frozen, not external effects or arbitrary database writes. Privileged SQL, nonparticipating writers and unsafe restores can invalidate the protocol.

`src/central/cooperative-lifecycle.ts` records reports in `central_cooperative_lifecycle_events`, not the normal command event table, and leaves the command row frozen as `claimed`. It checks the supervisor identity and active incarnation, requires that incarnation to own the claim, and uses an incarnation-scoped request ID to deduplicate identical reports and reject conflicting reuse. Report command IDs, request IDs and details must contain well-formed UTF-16; malformed strings are rejected before any write, a compatibility change for callers that previously submitted them. This does not repair earlier records or validate all other store inputs. Its allowed transitions are `claimed` to `accepted` or `rejected`, `accepted` to `running`, `completed` or `failed`, and `running` to `completed` or `failed`. These reports are visible through cooperative inspection, not normal command status or event reads. An exact claim request replay by the same active incarnation still returns the original claimed command after a completed report; the response is not permission to execute it again. A real consumer needs its own durable deduplication and execution safety, neither of which is established by this protocol. The legacy entry point does not initialize or expose this store; there is no integrated release, retry or recovery path.

`src/central/cooperative-mcp.ts` implements the cooperative tools used by the standalone app. It takes an authenticated supervisor principal and out-of-band incarnation credential, validates their shape, copies them into its closure and delegates to the stores. The standalone HTTP app supplies authentication and transport, but does not provision credentials. The MCP module sanitizes errors and rejects inputs or serialized responses containing the exact incarnation token; this is not general secret redaction. The central pre-commit claim guard also rejects responses containing the exact incarnation ID, which the adapter rejects too. This can leave an unsafe queued command at the head of its queue; it is not skipped. Claims already committed with that ID, including those made without this guard, can remain unreadable on replay and are not repaired. The adapter additionally rejects its local bearer and supervisor bearer. The central pre-commit guard does not check either; the local bearer is not available to central. A command containing one can therefore be claimed while its response is rejected; exact retries can remain unreadable. A local PostgreSQL integration test reproduced the committed claim, the rejected response and an unreadable exact retry using a synthetic local bearer. The test characterizes this known defect; it does not fix it. Do not automatically requeue such a claim. Do not mount legacy supervisor mutation routes alongside it. The legacy entry point mounts neither the cooperative app nor its stores.

Direct supervisor access to cooperative MCP can submit its own bearer in report text or request IDs. Central does not filter that bearer from reports. An in-memory HTTP test against committed code with a fake lifecycle store demonstrated the bearer reaching the store and being echoed in the response; the real store inserts report details and request IDs, but that database write was not tested in this experiment. Operators can read stored reports through inspection. Restrict direct access to trusted clients, protect reports as sensitive data, and do not put credentials in report fields. The adapter filters exact configured secret substrings, but this is not general redaction. No fix or credential rotation is implied.

`src/central/cooperative-settlement.ts` is the owner-approved recovery step for frozen claims (option A of `docs/claim-recovery-proposal.md`). An operator records one terminal settlement per claim with a disposition (`completed`, `failed`, `not-executed`, `unknown`), non-blank evidence and the latest lifecycle sequence they saw. Under the event lock it requires an existing claim, no earlier settlement, a claiming incarnation that is inactive or whose identity is retired, and an unchanged lifecycle sequence; otherwise it returns 404 or 409. Identical request-ID retries return the original with 200; conflicting reuse fails. Rows are immutable by trigger. Settlement changes no command, claim or lifecycle state, never requeues and never makes the command claimable. The runtime role has SELECT and INSERT on the settlement table only. Inactive incarnations and retired identities are never reactivated by current code, which is why the store does not lock those rows; it requires READ COMMITTED and refuses other isolation levels. The schema marker stays `fleet_cooperative_v1`: schemas are created fresh per start, so an older provisioned schema without the settlement table is not supported. Covered by `src/central/cooperative-settlement.test.ts` (PostgreSQL, including four concurrent settlements producing one record), `src/central/cooperative-settlement-route.test.ts` and the restricted-role process test in `src/central/cooperative-main.test.ts`.

Both cooperative operator routes decode the command ID from the raw route suffix and reject malformed percent encoding or UTF-8 with HTTP 400. The standalone app mounts these routes at the root. Custom Hono mounts that reuse `:id` in an outer prefix may see a compatibility change: the routes now use their own command ID rather than the outer parameter.

`transitionScoped` and optional request-store mutation guards provide transaction-bound hooks, but the server and MCP handlers do not wire them to incarnation validation. `transitionScoped` now passes a snapshot of its scope as the guard’s second argument; guards must use that argument and lock slot, identity and incarnation in `lockForClaim` order before the event lock. Existing one-argument guards still type-check but must be adapted if they relied on a mutable scope closure; the API cannot enforce this contract. Existing supervisor routes therefore do not gain incarnation fencing from these methods. Old deployed readers may not understand `claimed`; old writers and delivery workers may bypass the cooperative locking contract. Any eventual cutover must account for all readers and writers and needs a reviewed, tested compatibility and recovery design. There is no safe production migration procedure here; do not enable the prototype or remove its fence as a production cutover.

## Request array serialization gap

Direct in-process characterization of the local `Requests.create` with an in-memory SQLite database shows that ordinary sparse `evidence` and `allowedResponses` arrays, and dense arrays with a custom `toJSON` that returns a sparse array, persist holes as JSON `null`. A read returns those null entries. This is current behavior, not an intended invariant, and existing rows are not repaired. A separate direct in-process `CentralRequests.create` characterization with fake SQL shows ordinary sparse arrays serialized as `[null]` in INSERT parameters; it does not prove a PostgreSQL write or read. Neither characterization shows that these inputs can reach the stores through MCP. A candidate change is withheld and is not part of this committed implementation.

## Local command Unicode compatibility

Local command submission rejects malformed UTF-16 in the idempotency key, actor and text before lookup or insertion, and snapshots each input field once. Older SQLite writes may already have replaced malformed characters with U+FFFD. An invalid retry is rejected even if its normalized form exists; rejection does not prove the original was not committed and must not trigger submission under a new key. Existing rows are not repaired.

## Local actor size

Local command submission does not impose a separate actor length limit. With authentication disabled, the loopback REST command route accepts the actor supplied by the caller. Delivery escapes control characters in the actor header, expanding each to six ASCII characters; an offline test confirms the expansion, not service exhaustion. Large actors can increase storage and memory use. Existing records and exact replays need a compatibility decision before adding a limit.

## Local recipient response race

The local SQLite command state machine rejects recipient acceptance and rejection while a send is still `delivering`. A response can arrive after the text is visible but before the sender returns, so the response may fail and require a retry. This is reproduced with an in-memory database and a gated fake sender, not with live fleet. Simply allowing those transitions would let the later delivery result conflict with or overwrite the response; a fix must preserve both facts and cover restart recovery. Recipient authority is also not enforced in the local service.

## Delivery confirmation compatibility

`classify` now requires the expected target as its second argument. Exit code 0 counts as delivered only when raw stdout is exactly `<target>: delivered`, optionally followed by one LF or CRLF. `fleetSender` no longer trims stdout. Custom senders and direct callers that relied on substring matches, extra whitespace, or the old one-argument API must change. Previously recorded outcomes are not reclassified. A sender can spoof even an exact response; this check does not authenticate the sender or prove execution. Unconfirmed results remain unknown and are not automatically retried. Their new event detail is a fixed generic message rather than raw sender output, so prior CLI diagnostics are no longer available there; existing events are unchanged. `fleetSender` drains stdout and stderr concurrently to EOF, retaining at most 64 KiB per stream. If either stream exceeds the cap, is invalid UTF-8, or a reader or exit promise fails, both returned strings are empty and the exit code is -1, so the result is unconfirmed. Both readers and the child exit are awaited even when one fails. For valid output within the cap, stdout remains raw, including a UTF-8 BOM, and stderr remains trimmed. The `Sender` and `SendResult` types and existing two-argument `fleetSender` calls remain compatible; callers relying on large or invalid output, or the original exit code on capture failure, will see different results. The optional third argument injects a subprocess for tests. There is no timeout or process termination: the process or either pipe may hang. The success confirmation itself can include the target.

## Adapter deadline compatibility

The cooperative adapter checks a monotonic deadline after each request and response stream read, before forwarding, after the upstream fetch returns, and before returning a completed work result, in addition to its timer. Per-read checks stop continuously ready streams from starving the timer; an upstream body that returns after the deadline is cancelled rather than read, while expiry during body reads may still read one ready chunk first. Tests cover stream starvation, forwarding and late bodies, not each check in isolation. Requests that exceed the deadline before forwarding now return 504 without forwarding; after forwarding they return 504 with the existing unknown-outcome guidance, even if a late response would otherwise have been usable. This is a compatibility change for callers that previously received a late result. The timer and checks cannot preempt synchronous work or an uncooperative upstream; in-flight work and tracked cancellations can continue to occupy a concurrency slot. Unknown outcomes are not automatically retried. Offline tests use a controlled monotonic clock, not a live agent or network.

## Adapter process shutdown ordering

`src/host-agent/cooperative-main.ts` now sets the listener shutdown timeout to the adapter request deadline plus 2 seconds (30 s + 2 s by default). Previously the listener force-closed sockets after 5 s while a forwarded request could still be waiting up to 30 s, so SIGINT or SIGTERM reset the client connection instead of returning the adapter's 504 "outcome unknown" response. The process can now stay alive up to 32 s after a signal while forwarded work drains. Uncooperative handlers can still be force-closed after that, and a reset still does not mean the effect did not happen. `startCooperativeAdapter` takes an optional second argument for the request deadline; existing one-argument calls stay signature-compatible but now wait up to 32 s instead of 5 s on shutdown. Request deadlines within 2 s of the 2,147,483,647 ms timer limit make the shutdown timeout invalid and fail startup. The regression test uses a loopback stub central, not a live agent.

## Central process shutdown

`src/central/cooperative-main.ts` now installs SIGINT and SIGTERM handlers after a successful start. `stop()` stops accepting connections and waits for accepted requests to finish and reply, up to a 10 s grace deadline (`CENTRAL_SHUTDOWN_GRACE_MS`; `startCooperative` takes an optional `shutdownGraceMs` for tests). After the deadline it force-closes connections. It then always waits, without a bound, for tracked request handlers and their SQL work before closing the pool, so a stuck transaction can delay exit indefinitely. A force-closed client gets a connection reset even if its command committed: the outcome is unknown, not failed, and must not be blindly retried. Previously `stop()` force-closed immediately and the CLI had no signal handler, so a signal killed the process mid-request. Both handlers are removed once stopping begins, so a second SIGINT or SIGTERM gets the default action and kills the process at once, with the same unknown-outcome risk. A failed stop sets exit code 1 and prints a generic message without tokens. Offline tests run the real entry point in a child process with fake SQL and stores; no PostgreSQL behavior is established.

The legacy `src/central/main.ts` entry point now has the same shutdown semantics: SIGINT and SIGTERM handlers after a successful start, a graceful `stop()` bounded by the same 10 s grace (its own `CENTRAL_SHUTDOWN_GRACE_MS`; `startCentral` takes an optional third argument `{ shutdownGraceMs }`, validated as 1 to 2,147,483,647 ms before any I/O), then an unbounded wait for tracked handlers before the pool closes. A second signal kills the process at once. When stopping begins it closes accepted host WebSockets on `/api/host/socket` with code 1001 and closes any socket that finishes opening later, so idle hosts no longer hold shutdown for the full grace period. Hosts then reconnect and republish inventory. Inventory is process-local, so nothing durable is lost. Previously `stop()` force-closed immediately, so a command that committed during shutdown reached its client as a connection reset. Offline tests drive real loopback requests with an injected fake SQL client and run the real entry point in a child process; no PostgreSQL behavior is established.

## Central credentials file

`COOPERATIVE_CREDENTIALS_FILE` must now be an absolute path to a regular file owned by the current user with no group or other permissions, at most 1 MiB of valid UTF-8, and not a final-component symlink. These are the adapter config checks, except the size limit (adapter config: 64 KiB). Startup rejects anything else with the same generic error, before any SQL client is created. Existing setups with a relative path, a 0644 file or a symlink will fail to start until fixed. Same-UID processes remain trusted, and parent directory symlinks are still followed. The legacy `src/central/main.ts` entry point is unchanged.

## Adapter JSON text secret screening

The cooperative adapter checks each valid JSON text block in `result.content` for its configured tokens and incarnation ID in decoded JSON string keys and values, including duplicate keys. The existing 2 MiB upstream response byte limit bounds the scan. A match returns the existing generic unknown outcome after forwarding; it does not retry. Non-JSON text keeps the previous checks, and JSON embedded inside a JSON string is not recursively decoded. This is a narrow exact-substring check, not general secret detection or a guarantee against other encodings, split secrets, or untrusted same-UID processes. A rejected response may follow a committed operation; do not infer that it did not happen.

## Central Origin compatibility

The legacy and cooperative central apps permit an absent Origin, but require every present value, including an empty string, to match `allowedOrigins` exactly. An undefined or empty allowlist rejects every present Origin. Previously an empty Origin bypassed the check in both apps. Clients sending an empty header now receive 403 unless the empty string is explicitly allowed. Neither central entry point configures an allowlist. The offline regressions exercise in-process requests, not a network proxy or browser. Host socket Origin handling is unchanged.

## Limits and safety

- **No real agent dispatch:** the mounted socket is inventory-only; the entry point does not wire delivery attempts or start a host-agent process. The dispatch message has no runtime instance ID, although the separate executor requires one. Do not treat the isolated components as an end-to-end delivery path.
- **Identity enrollment is trusted, not runtime fencing:** supervisor run ownership uses the configured name, `principalId`, host ID and session together. Startup requires an exact active PostgreSQL registry binding, and each authenticated supervisor HTTP request rechecks it, failing closed on a mismatch or lookup error. Enrollment is an explicit trusted operator action; existing credentials are not automatically migrated. An ID cannot be rebound or re-enrolled after retirement while its registry record is retained. This does not establish a runtime-incarnation fence: command scope remains host and session name, and the registry can be bypassed or lost by someone with database write access or an unsafe restore. Legacy supervisor MCP command reads, mutations and request tools now check the active identity inside their store transaction. Scoped command reads, transitions and event reads reject malformed UTF-16 identifiers and invalid scopes before the guard. Command reads, event filters and command list filters also reject malformed UTF-16; direct callers that previously passed those values now fail. This does not repair existing data. The identity lock precedes event and object locks; an operation holding it first may commit before retirement. Supervisor calls fail closed when the required registry or scoped store is unavailable, which changes compatibility for custom integrations. Fake transaction tests cover dispatch and denial, but do not prove PostgreSQL lock ordering. This identity check is not an incarnation fence and does not cancel external effects.
- **Pagination is not a snapshot:** REST `GET /api/commands` and MCP `command_list` and `request_list` expose `limit`, `cursor` and `nextCursor`. Legacy pages default to 100 records and allow 1 to 1,000, ordered by creation time and ID. Cooperative operator MCP command pages default to and allow at most four records. Clients should retain the same filters while traversing. The keyset traversal does not hold a snapshot: concurrent inserts or status changes can cause records to be missed. The request gate uses a separate query. Run lists and event queries remain unbounded; event queries accept `afterSeq` but have no result limit. The direct `CentralRequests.events` API is global rather than owner-scoped and must not be exposed to a scoped caller without additional authorization. Central MCP does not currently expose `request_events`. `request_list` also returns the unbounded run list on each page.
- **Cooperative operator MCP read limits:** `command_get` and `command_list` use bounded store methods and a 2 MiB serialized JSON-RPC response budget. The list defaults to and permits at most four records; clients requesting larger pages must change. SQL masks oversized returned rows, while an oversized lookahead does not prevent returning the preceding page. Oversized reads fail explicitly. An oversized row blocks traversal past that row; there is no skip cursor or repair workflow. These limits do not bound physical database I/O or all MCP methods. The cooperative app rejects an injected request store. The app rejects JSON-RPC batches, rejects malformed UTF-8 before dispatch instead of replacing invalid bytes, and its ID guard allows null, strings of at most 256 UTF-16 code units, or safe integers through to the MCP transport. The transport rejects null IDs with HTTP 400; the host-side adapter rejects them before forwarding. Clients sending malformed UTF-8 must correct their encoding. Mutation responses are not subject to the read budget, to avoid reporting failure after a committed mutation.
- **Legacy HTTP input:** legacy MCP POST rejects malformed UTF-8 with a JSON-RPC parse error before dispatch, rather than allowing replacement decoding. For malformed bodies this check precedes the SDK Accept and Content-Type validation. Oversized streamed REST and MCP requests handle rejected cancellation promises while returning HTTP 413. Cancellation is best effort and does not prove upstream work stopped.
- **Cursor scope:** command and request cursors include their filters, but are not signed and must not be treated as authorization. Legacy request-list filters and run, request and gate read identifiers reject NUL and malformed UTF-16 before SQL. Legacy request mutation lookup IDs and registration actor are also checked before their transaction and guard. Command IDs containing NUL or malformed UTF-16 are rejected by get, getBounded, transition, events and their scoped variants before SQL. Command host and session scope filters containing NUL are rejected before the data query; scoped operations reject them before the identity guard. Scoped command transitions reject malformed UTF-16 and NUL in event actor and detail after authorization and conflict checks, before writes. The unscoped transition does not yet apply this event encoding validation. Direct callers that previously supplied NUL now receive a validation error or access denied. A new run phase is checked after lookup, while replay of an existing run continues to ignore the supplied phase. Phase updates validate actor, phase and status after the guard, ownership and revision checks; untyped callers passing null phase now receive an error instead of a fallback; callers using these values must change. Request creation also rejects NUL and malformed UTF-16 in origin, question, proposed action, scope, evidence and allowed responses after ownership and revision checks; existing records are unchanged. New resolutions reject NUL and malformed UTF-16 in the normalized actor, response and note after replay, status and allowed-response checks; exact legacy replays still return without rewriting. New acknowledgement and withdrawal events reject NUL and malformed UTF-16 in the actor after owner, status and replay checks. Withdrawal reason encoding is not yet validated. A malformed scoped-gate input is rejected before the transactional identity guard, so it can return invalid instead of access denied without reading prot... (line truncated to 2000 chars)
- **The phase gate is informational, not authorization:** `request_gate` reports the approval state for a phase and revision. It does not prevent the supervisor from updating the phase or performing work, and acknowledgement does not start a phase. Central request gate and mutation transactions acquire the shared event lock before run or request locks. They fail closed if the singleton lock row is absent; initialization normally creates it. This changes behavior for incomplete schemas and does not repair them. This serialization matters: phase updates lock a run before requests, while resolution and status changes lock a request before its run; bypassing or removing the event lock can expose a deadlock. This is a source-level lock-order analysis, not a PostgreSQL concurrency test. Local host gate reads use one SQLite transaction, but a caller-owned outer transaction can expose uncommitted data, and neither gate fences a later action. The legacy gate query considers open approvals and the literal responses `approve` and `decline`; it ignores resolved or acknowledged approvals with other allowed responses. Another approval can therefore make the gate report approved while such a response exists. A custom response alone can be reported as no approval request. The meaning of mixed custom responses is not established; do not interpret the gate as evaluating them. The separate local host gate checks an approval before an open request for the same run, phase and revision, so it can report approved while another approval remains unanswered. This differs from the central gate. Mixed-approval policy remains unsettled; neither result proves human authorization.
- **Executor isolation is not established:** the legacy `Deliverer` serializes only its own calls. An in-memory test with two instances sharing a command store shows overlapping fake sends to one target; it does not demonstrate real paste interleaving. The normal entry point constructs one instance, but no fence covers other instances, processes or senders. Each `DeliveryExecutor` has its own queue. An offline test with a shared in-memory journal shows that two instances can overlap sends for different attempt IDs. The journal deduplicates IDs, not targets or active executors. No integrated executor runtime is established; safe startup reconciliation and delivery require exclusive ownership that also covers other processes and senders.
- **Recovery is not automatic:** methods exist to mark interrupted central delivery as unknown, but startup does not call them. Their documented precondition is that previous delivery workers have stopped. The host journal has its own explicit recovery method. None of this establishes a safe coordinated restart or retry protocol.
- **No safe restore procedure is implemented or verified.** `scripts/central-backup.ts` invokes `pg_dump` in custom format with TLS `verify-full`, requires an explicit PostgreSQL URL and a new output path, and leaves an incomplete file on failure. It does not validate an archive against its source, create a second copy, restore it, or reconcile it with host journals. A dump file alone is not a verified backup. `scripts/central-backup-check.ts <archive>` is a read-only first step: it opens the file without following a final symlink, feeds that descriptor to `pg_restore --list` with no `PG*` variables and no database connection, requires a custom-format table of contents, and prints the SHA-256, size, TOC entry count and source database name. It hashes and lists the same single pass over the file and fails if the file changes size or modification time while being read. A manual run against a dump of the local test database passed, and the same archive cut to its first 100 bytes failed. It reads only the table of contents, so an archive whose data section is truncated or corrupt can still pass. It does not restore, compare with the source or prove a second copy. A manual restore rehearsal on 2026-11-12 (owner-approved) dumped the local test database with `pg_dump -Fc` inside the test container and restored it with `pg_restore --exit-on-error --no-owner` into a new throwaway database: all 26 tables matched by row count and an MD5 of sorted rows (60,188 rows), and trigger and constraint counts matched (2 and 53). The throwaway database was then dropped. It used the same server, a superuser and `--no-owner`, and did not compare grants or role ownership; it is a rehearsal, not a restore procedure.
- The legacy entry point binds to loopback only. Optional TLS: set both `CENTRAL_TLS_CERT_FILE` and `CENTRAL_TLS_KEY_FILE` to absolute PEM paths and it serves HTTPS and `wss:` on that loopback port. Startup fails before the database opens if the pair is incomplete or unreadable, or if the certificate does not parse or match the key. A local test with a throwaway self-signed certificate shows a host client publishing inventory over `wss:` when it trusts the CA; without the CA, both HTTPS and the host client are refused and no inventory appears. TLS does not permit a non-loopback bind, and no certificate provisioning, rotation or deployment is established. The cooperative entry point accepts the same optional pair as `COOPERATIVE_TLS_CERT_FILE` and `COOPERATIVE_TLS_KEY_FILE`; it checks the files before provisioning any schema and prints an `https:` URL. On both entry points the key file must be a regular file owned by the running user with no group or other access, opened without following a final symlink, at most 64 KiB; the certificate has no mode rule. A PostgreSQL-backed local test submits and inspects a command over HTTPS with the CA trusted, and is refused without it. The adapter process config accepts an optional absolute `centralCaFile` (a parseable PEM certificate in a regular file of at most 64 KiB, not a symlink; `https:` central only), used for central requests; without it the default trust store applies. In the same test an adapter without the CA cannot claim and the command stays queued, while an adapter given the CA claims it over HTTPS. The mounted inventory socket does not establish a connected host-agent runtime. There is no production deployment, complete authentication lifecycle, restore workflow or live-agent operation established by these files. Parallel implementation is unsettled; this page describes only the local source inspected and should be rechecked before relying on it.

## Local configuration

For an isolated local experiment, provide `CENTRAL_DATABASE_URL` for a PostgreSQL database and `CENTRAL_CREDENTIALS_FILE` for a readable JSON file outside the repository. `CENTRAL_PORT` is optional and defaults to `4872`; if set it must be between 1 and 65535. `CENTRAL_HOST`, if set, must be exactly `127.0.0.1`. Start with `bun src/central/main.ts`. Startup creates tables in the configured database, so use a dedicated local database, not production data.

The credentials file is a nonempty JSON array of objects with `tokenHash` and `principal`. `tokenHash` is a lowercase SHA-256 hex digest of the bearer token, not the token itself. A principal has `name` and `role`; a `host` also needs `hostId`, and a `supervisor` needs `principalId`, `hostId` and `session`. Names, token hashes and supervisor principal IDs must be unique within the file. Principal names and scope identifiers must be well-formed UTF-16; malformed existing configuration now fails startup. Before startup, a trusted operator must enroll each supervisor tuple in the same database, for example with `DATABASE_URL` set outside the command line: `bun src/central/identity-cli.ts enroll --principal-id ID --name NAME --host-id HOST --session SESSION`. Use `retire` with the same flags to retire a binding. The CLI initializes the registry table and has no automatic migration or credential-file update. Retired configured supervisors prevent the next startup until credentials are updated. Keep the file, tokens and database URL private; do not commit secrets. Credentials are loaded at startup.

## Tests and legacy service

Select and inspect individual test files before running them; the broad `src/central` and `src/host-agent` suites include fleet or tmux tests and are not authorized by default. PostgreSQL integration tests are skipped without `CENTRAL_TEST_DATABASE_URL`; the legacy loopback integration test requires a disposable local database named `fleet_control_test` on `127.0.0.1`. Use only a dedicated disposable test database, since tests initialize and write database objects. The cooperative loopback test assembles the standalone app and stores in a random schema, exercises synthetic submission, claim, reports, inspection and replacement fencing, and drops that schema afterward. It is not a running agent integration. Cooperative-claim tests also isolate their search paths and check the trigger schema. The delivery-attempt versus claim race test does not establish that the claim was blocked before the lock holder releases, so it is not proof of that contention order. They do not remove a pre-existing trigger in `public`. A public trigger was reported in the disposable test database; its current presence has not been checked in this documentation pass. It is outside isolated test cleanup and can affect other tests using public tables. Do not infer its absence or removal from these tests. A skipped integration test is not a pass against PostgreSQL.

The process-test cleanup chains can replace an earlier test failure with a later cleanup failure. A failure while stopping or awaiting a child can also skip later cleanup or allow schema removal before all children are confirmed exited. Even confirmed child exit does not prove that an already submitted PostgreSQL operation has finished. These tests do not establish safe cleanup under failure; inspect retained resources independently, and do not assume that killing a child cancels database work. The role fixture reports its generated role when creation has an unknown outcome or role removal fails, without including the underlying database error.
